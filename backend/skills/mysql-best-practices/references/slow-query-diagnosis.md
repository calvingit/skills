# 慢 SQL 与延迟异常

用于调查单条 SQL 变慢、整体吞吐下降、尾延迟升高或周期性抖动。目标是确定瓶颈类型，不能看到某个执行计划字段后就立即修改 SQL 或索引。

## 最小证据集

优先收集以下信息，无法获得的项目明确标为未知：

- MySQL 版本、发行版、实例角色和问题时间窗口；
- SQL digest 或已脱敏语句、参数类型、调用频率、并发度和超时位置；
- 表结构、现有索引、近似行数、数据分布，以及近期表结构或数据量变化；
- `EXPLAIN`，必要时使用 `FORMAT=JSON`；只有满足安全条件时才使用 `EXPLAIN ANALYZE`；
- 延迟分位数、执行次数、检查与返回行数、锁等待、临时表、排序和错误数；
- 同期 CPU、I/O、内存、磁盘、连接数、事务和复制指标；
- 问题发生前后的发布、参数、统计信息、流量或数据倾斜变化。

如果 `sys` schema 可用，可以从聚合数据中寻找总耗时和调用量的主要来源：

```sql
SELECT query, db, exec_count, total_latency, avg_latency,
       lock_latency, rows_examined, rows_sent, tmp_disk_tables,
       full_scan, first_seen, last_seen
FROM sys.statement_analysis
LIMIT 20;
```

该视图基于 Performance Schema 的聚合数据。使用前确认采集已经开启、计数器覆盖的时间窗口和当前执行权限。输出可能包含业务信息，分享前需要脱敏。

## 诊断顺序

1. **确认症状**：区分平均延迟、尾延迟、吞吐和超时；确认问题来自单个 digest、单个租户、单个节点，还是整个实例。
2. **分解总成本**：总耗时约等于调用次数乘以单次耗时。先判断主要问题是调用次数暴涨，还是单次执行变慢。
3. **对照执行计划与数据**：检查访问路径、估算行数与实际分布、连接顺序、回表、排序、临时表和分区裁剪；不要孤立解读 `type` 或 `Extra`。
4. **排除等待放大**：锁等待、磁盘抖动、buffer pool 命中下降、连接排队和从副本读取都可能表现为“SQL 变慢”。
5. **定位变化点**：检查统计信息、索引可见性、参数、表结构、数据倾斜、发布、流量和缓存冷热变化。
6. **进行最小范围实验**：一次只改变一个主要变量，并使用相同的参数分布、并发和缓存条件进行对比。

## 常见疑难点

- **隐式类型转换或字符集与排序规则转换**：可能改变索引的使用方式；核对列类型、绑定参数类型和比较两侧的字符集。
- **数据倾斜与执行计划变化**：平均分布不能代表热点值。核对估算和真实基数，必要时评估统计信息或直方图，不能直接固定执行计划。
- **深分页**：大 `OFFSET` 仍需扫描并丢弃大量记录。业务语义允许时，使用稳定且唯一的排序键进行 keyset pagination。
- **N+1 与请求放大**：单条 SQL 即使很快，每个请求执行次数过高也可能拖垮实例；应结合调用链和 digest 次数确认。
- **超大 `IN`、宽行与无界结果集**：解析、网络、序列化和应用内存也可能成为瓶颈，不能只观察数据库执行时间。
- **排序和磁盘临时表**：这些是需要继续调查的信号，不一定代表缺少索引；应核对查询语义、结果规模、行宽和内存压力。
- **冷缓存基准**：单次执行结果不能代表线上稳定状态；需要明确预热方式、重复次数和并发条件。

## 优化建议要求

任何优化建议都必须说明：它针对哪个已经证实的瓶颈、会增加哪些写入或资源成本、如何在可比时间窗口内验证，以及无收益或发生回归时如何撤回。单次延迟下降但总调用量、锁范围或复制压力明显增加，不能视为优化完成。

参考：[MySQL 8.4 `sys.statement_analysis`](https://dev.mysql.com/doc/refman/8.4/en/sys-statement-analysis.html)、[MySQL 8.4 `EXPLAIN`](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。
