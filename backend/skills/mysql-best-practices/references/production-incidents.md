# 生产事故处置

用于处理连接耗尽、CPU、I/O 或磁盘异常、复制延迟、实例不稳定和崩溃恢复。事故中应先稳定服务并保存关键证据，再修复根因；所有有副作用的操作都应遵循现有故障指挥与授权流程。

## 处置步骤

1. 明确用户影响、开始时间、受影响的节点或租户，以及当前正在执行的变更。
2. 保存关键时间线和只读证据，不要为了尽快恢复现场而先重启或清空指标。
3. 选择可逆的止损措施：获得批准后降低入口流量、暂停批量任务、限制高成本功能或隔离异常调用方。
4. 每次操作只改变少量变量，记录时间、操作者、预期结果和实际效果。
5. 指标恢复后继续观察，区分临时缓解和根因修复，并补齐复盘需要的证据。

## 连接耗尽

连接数达到上限可能由流量突增、连接池泄漏、慢 SQL、锁队列、事务未结束、连接建立风暴或实例资源不足引起。先核对活动与空闲连接、连接创建速率、会话持续时间、来源、等待事件、线程和应用连接池配置。

直接提高 `max_connections` 可能增加内存占用、调度成本和下游争用，并把真正的过载点推迟到其他资源。只有确认容量充足、上游连接需求合理且有恢复原值的方案时，才把它作为临时措施。

## CPU 或 I/O 饱和

- CPU 高：区分调用量、单次成本、解析或排序、并发和后台任务，同时检查主机 steal、throttling 和平台配额。
- I/O 高：区分数据页读取、脏页刷写、redo、binlog、临时表、备份、DDL 和存储层抖动。
- buffer pool 命中率或磁盘利用率只能提供线索，不能单独证明根因；需要与查询、时间线和等待事件交叉验证。
- 不在事故中同时修改多个全局参数。参数变更必须记录原值、作用域、持久化方式、内存上限和恢复步骤。

## 磁盘逼近上限

先识别空间增长来自数据或索引、binlog、relay log、redo、undo、临时文件、错误或慢日志、备份，还是在线 DDL 的影子对象。删除文件前确认 MySQL 和平台的生命周期管理方式，不能直接移除正在使用的数据库文件。

紧急清理也要保留恢复和审计所需的数据。扩容只能争取处理时间，随后仍需解决持续增长原因、保留策略和告警提前量。

## 复制延迟

确认复制技术和拓扑，再区分 source 生成速度过快、网络或存储异常、单线程或依赖限制、大事务、DDL、冲突或错误，以及 replica 查询竞争。延迟指标必须结合 relay log、应用与提交进度和复制线程状态理解。

不要默认把读取流量切到落后的副本。先确认业务是否能接受陈旧读取、读后写不一致和故障切换的影响。跳过复制错误、重置复制位置或重新搭建副本都需要明确的数据一致性方案。

## 崩溃与恢复

- 先保存日志、版本、启动参数、磁盘状态和最近变更；反复无目的重启可能覆盖证据并增加恢复压力。
- 优先使用正常崩溃恢复、已验证备份或新实例恢复，不直接修改 InnoDB 文件。
- `innodb_force_recovery` 只用于无法正常启动时的数据抢救，并应在独立物理副本上从低级别开始。级别 4 及以上存在永久损坏风险；目标是尽快导出可读数据，不能让该实例恢复生产服务。
- 任何故障转移都要核对数据落后量、写入隔离、防脑裂措施和回切条件。

参考：[MySQL 8.4 Forcing InnoDB Recovery](https://dev.mysql.com/doc/refman/8.4/en/forcing-innodb-recovery.html)、[MySQL 8.4 Replication Troubleshooting](https://dev.mysql.com/doc/refman/8.4/en/replication-problems.html)。
