# 投递与任务持有权

## 分开确认各阶段

记录实际顺序，并分别标出业务状态变更、消息发送、消息代理（broker）接收、发布确认（publisher confirm）、消费者领取、副作用完成和消费确认。不要把 broker 接收、发布确认或持久化合并成同一个阶段；它们的关系取决于实际协议和配置。发布确认不等于消费者已处理，消费者收到消息，也不代表业务结果已经持久化。

检查每个相邻阶段之间崩溃、断连或超时的后果。副作用之前确认可能丢失工作，副作用之后确认可能因中断重投；两者的选择必须满足已确认业务约定，不能只调整 ack 的位置就声称问题已经解决。

消息 ID、投递尝试（attempt）与业务操作 ID 不一定相同。重试、转入死信队列（DLQ）或重新发布时，核对哪些标识保留；传输层去重期限不自动覆盖业务重试与人工重放期限。

## 任务持有权与执行生命周期

核对消费者组、租约、可见性超时（visibility timeout）、分区分配与重平衡。这里的任务持有权指实际消费分配或租约授予的处理资格，不自动保证独占投递；例如 SQS 的 visibility timeout 本身不排除重复投递。失去这种资格不会自动停止已发出的数据库或外部调用；续租失败或重平衡后的旧执行者可能和新执行者并发写入。

需要保证只有当前持有者能产生业务效果时，检查业务持久化边界能否拒绝旧版本或重复操作，而不是只延长租约。消费者并行处理时，确认累计提交的消费位点不会越过尚未完成的消息，逐条确认时也不能将未完成消息标为成功；处理完成顺序不一定等于领取顺序。

关闭时应先停止领取新任务，再处理或释放在途工作，并在部署允许的终止时间内完成。不要把未完成任务标为成功来使进程顺利退出。任务超时与外部操作结果未知分别处理。

## Webhook 接收

核对签名、密钥轮换、时间窗口及来源语义，不信任载荷自报身份。使用供应方要求的原始字节验签；签名正确不证明消息未重复或授权仍有效。

返回成功前，应满足供应方与本地约定的接收条件，例如先持久化消息，再异步处理。不能先响应成功再仅把消息留在进程内存，也不能一律等待全部业务处理才返回而忽略发送方超时与重投。按实际协议决定。

资料：[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)、[SQS 可见性超时（visibility timeout）](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)。
