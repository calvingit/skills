# 数据库规约

> 基线：阿里巴巴 Java 开发手册（黄山版）。用于 Java 服务涉及 MySQL、SQL、ORM 或 DAO 时的按需检查。

## 表设计

- 表名、字段名保持项目统一命名规则，语义明确，避免保留字和难以理解的缩写。
- 字段类型按真实数据范围选择；不要用字符串代替本应有明确类型的数据。
- 金额和精度敏感数值使用适合的精确类型，不用浮点数承载精确金额语义。
- 时间字段的类型、时区和精度遵循项目统一策略，避免同一系统内存在多套约定。
- 是否允许 `NULL`，以及默认值、逻辑删除、审计字段等设计，应以业务语义和项目规范为准，不机械套用模板。

## 索引

- 索引围绕真实查询、排序、关联和唯一性约束设计，不以“可能有用”为理由堆积索引。
- 联合索引的字段顺序应结合查询条件、选择性和实际执行计划判断。
- 对唯一业务约束，优先考虑由数据库唯一约束提供最终一致性保护，不能只靠应用层先查后写。
- 修改索引前评估写入、存储和现有查询的影响，并用执行计划或实际指标验证。

## SQL

- 禁止将不可信输入直接拼接进 SQL；使用参数绑定或 ORM 提供的安全接口。
- 查询应明确列出需要的字段，避免不必要的 `SELECT *`，尤其是稳定接口和高频查询。
- 大结果集必须考虑分页、流式读取、批处理或明确的数量上限。
- 批量写入应避免逐条远程往返造成明显性能问题，但批量大小必须受资源限制。
- 复杂 SQL 应先保证语义正确且可以验证，再考虑细节优化；性能判断应基于执行计划和实际数据分布。
- 事务范围保持必要且清楚，避免把不可控的远程调用或耗时计算放进数据库事务。

## ORM 与 DAO

- Entity、DO、DTO、VO 等对象职责遵循项目既有分层，不为符合命名习惯额外增加转换层。
- 明确懒加载、级联、批量加载和 N+1 查询等 ORM 行为，不假设框架会自动生成合理 SQL。
- 更新操作应明确更新字段和并发语义；涉及竞争写入时，根据业务选择唯一约束、乐观锁、悲观锁或其他一致性机制。
- DAO 或 Repository 层不要泄露与上层无关的数据库实现细节，也不要为了抽象而增加没有语义价值的包装层。

## 验证

数据库相关修改至少应根据影响范围选择以下验证方式：

- migration 或 DDL 能在目标数据库版本执行；
- 关键 SQL 使用执行计划检查索引和扫描范围；
- 对事务、唯一约束和并发写入进行针对性验证；
- ORM 变更检查实际生成的 SQL，不能只看 Java 调用的表面行为。

无法在当前环境验证数据库行为时，明确说明未验证项，不把静态阅读当作运行验证。
