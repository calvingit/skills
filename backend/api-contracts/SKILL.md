# API 契约与演进

检查改动是否影响调用权限、可观察结果，以及现有调用方能否继续使用接口。适用于明确涉及接口契约、Schema、兼容性或契约验证的任务；普通内部重构不自动升级为契约设计。

## 工作方式

1. 找到项目契约的权威来源与生成方向：已确认需求、SPEC、OpenAPI/JSON Schema/事件 Schema、代码注解或 IDL，以及实现、网关、客户端、消费者和现有测试。确认协议、Schema 方言和工具版本，不假定文件名代表权威。
2. 以当前发布契约或可复核版本为基线，定位本次差异与受影响调用方，包括旧客户端、独立发布服务和历史消息。未列全的消费者明确记为未知。
3. 按下表核对数据结构、接口行为和需要兼容的版本组合。契约与实现冲突时报告差异并核实应有行为，不把 Schema 自动改成当前实现，也不从生成代码反推需求。
4. 在已授权范围内修改契约源文件、实现或测试，并使用项目现有工具重新生成受影响产物。只审查时不修改。外部行为、权限或兼容策略尚未确定时，交由需求负责方确认，只暂停受影响的部分。
5. 用真实入口、已支持调用方和版本组合验证。报告契约变化、受影响方、迁移或发布顺序、实际证据及未验证项，不把格式校验等同于兼容性证明。

## 职责与边界

- 本 Skill 提供技术判断，不另建一套需求依据。使用本仓库工程流程时，外部行为归已确认需求和 SPEC，共享接口设计归 HLD；无这些文件时使用调用方明确的契约，不强制补建文档。
- API 与事件 Schema 的兼容性在此统一处理。消息投递、消费任务的持有权、重放与业务副作用属于 `event-driven-backend`；不要在这里设计新的调度或重试系统。
- 复用项目现有协议、版本方式、错误格式和工具。不要为一次字段变更新增 API 版本、Schema Registry 或契约平台，除非有明确需要。
- Schema 声明的安全要求不替代运行时资源授权。修改文档的授权不包括调用生产接口、向 Schema Registry 注册或发布 Schema、发布 SDK、通知外部消费者，或宣布弃用（deprecation）及移除接口。
- 这些资料提供验证方法，最终验收仍由调用方的既有流程负责；不改验收条件来迁就实现。
