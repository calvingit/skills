# 兼容性与版本

## 指明谁与谁兼容

根据本次发布需要，至少检查旧调用方→新服务、新调用方→旧服务这两种组合。对事件，还要检查旧消费者读取新事件、新消费者读取历史事件的情况。列出发布、回滚及重放期间实际存在的组合，不能用“向后兼容”替代方向和版本范围。

请求是服务接收的数据，响应是客户端接收的数据；相同字段修改在两个方向上影响不同。结合实际解码器、生成类型、默认值和业务分支判断：

| 变化 | 需要验证 |
| --- | --- |
| 请求新增必填字段或收紧取值 | 旧请求是否被拒绝；缺失、null 与默认处理是否符合约定 |
| 响应删除字段、改变类型或允许 null | 旧客户端的必填假设、反序列化及业务处理 |
| 新增响应字段或枚举值 | 严格解码器、枚举值的穷尽分支和未知值策略；“只增加”不保证安全 |
| 修改默认排序、分页、单位、错误或权限 | Schema 可能未变，但可观察行为已经变化 |
| 事件字段演进 | 编码格式中写入方与读取方（writer/reader）的解析规则、消费者版本及历史积压 |

字段重命名通常同时涉及删除与新增。兼容别名、双读或双写须有已确认的支持窗口与退出条件，不无限保留；不要要求所有客户端同时升级，除非部署模型确实保证。

## 发布和退出

沿用现有版本与弃用策略。说明哪些接收方先支持新格式、何时允许生产者发送、旧版本何时可移除，以及回滚能否读取已产生的新数据。只有观察到调用方迁移或满足已确认支持政策后，才能建议移除旧契约。

低流量或短期未调用不证明外部调用方已消失。弃用标记和版本号只是沟通手段，不使不兼容变更自动兼容；对未知客户端明确覆盖限制。

Schema Registry 的兼容检查比较不同版本的 Schema，判断它们是否满足所配置的兼容方向和历史版本范围（例如 backward/forward、transitive）。这不是对实际消息载荷的校验，也不能证明业务含义、权限、顺序或副作用没有变化。重放可能使用当前代码处理旧消息，需与消费生命周期检查配合。

资料：[OpenAPI 规范及历史版本](https://spec.openapis.org/oas/latest.html)、[Protocol Buffers 更新消息类型](https://protobuf.dev/programming-guides/proto3/#updating)。具体格式使用项目版本的解析规则，不将 Protobuf 的规则套用于 JSON 或 Avro。Schema Registry 的检查范围参见[版本兼容规则](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)，其他实现应核对各自文档。
