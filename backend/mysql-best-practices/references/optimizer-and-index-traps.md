# 优化器与索引陷阱

用于调查执行计划异常、设计复合索引、增删索引、处理统计信息偏差，以及判断优化器提示是否适用。

## 判断原则

- 索引可能承担定位、过滤、排序、覆盖和约束等不同职责，不能只用“是否走索引”评价其价值。
- 复合索引的列顺序由真实查询形式、等值或范围条件、排序分组、覆盖需求、数据分布和写入成本共同决定。
- “范围条件之后的列完全无用”并不准确：后续列可能仍参与索引条件下推、过滤或覆盖，只是未必继续缩小访问范围。
- “选择性最高的列永远放第一”也不成立。唯一点查、前缀复用、排序、范围扫描和压缩效果都可能改变结论。
- `ALL`、`Using filesort`、`Using temporary` 是调查线索，不代表一定存在故障。小表扫描或小结果集排序可能比复杂索引路径成本更低。
- 优化器成本是估算结果。应比较估算行数、真实基数、数据倾斜和运行指标，不能只看成本数字。

## 新增索引前

1. 收集查询频率、延迟贡献、参数分布、表结构、现有索引和执行计划。
2. 确认索引针对的是已经证实的瓶颈，而不是一次偶发样本。
3. 检查能否复用或调整现有索引，避免大量前缀重叠的索引。
4. 评估存储、buffer pool 占用、页分裂、写放大、复制和 DDL 成本。
5. 用代表性数据和并发条件验证读取收益与写入回归，并准备撤回方案。

不要为了覆盖查询而把大字段机械加入索引。覆盖收益必须与索引体积、更新频率和页利用率一起评估。

## 删除索引前

- 确认观察窗口覆盖业务周期、定时任务和低频关键路径；“最近没用”不代表“可以删除”。
- 排查索引是否用于唯一约束、外键支持、锁范围控制或灾备和运维查询。
- 版本和平台支持时，可先将候选索引设为 invisible，观察执行计划和性能，再决定是否物理删除。不可见索引仍会被维护，唯一性仍然生效，因此它只能模拟优化器不可见，不能模拟删除后的写入收益。
- 删除后的回退需要重建索引；大表重建可能成本很高，不能将其描述为瞬时回滚。

## 统计信息与执行计划变化

估算基数明显偏离实际数据分布时，先确认统计信息是否陈旧、采样是否能代表热点值，以及相关列之间是否存在关联。直方图可能改善部分谓词估算，但也有维护成本和版本差异；更新统计信息还可能改变其他 SQL 的执行计划，必须观察受影响范围。

## 优化器提示与强制索引

优化器提示（optimizer hint）或 `FORCE INDEX` 可以用于可控的诊断实验或临时缓解，但不能替代根因分析。使用前记录适用 SQL 范围、数据分布假设、版本行为、退出条件和后续修复。随着数据增长，当前正确的强制路径以后也可能引发故障。

参考：[MySQL 8.4 Invisible Indexes](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html)、[MySQL 8.4 Optimizer Statistics](https://dev.mysql.com/doc/refman/8.4/en/optimizer-statistics.html)。
