# 优化器与索引陷阱

用于执行计划异常、复合索引设计、索引增删、统计信息偏差以及 optimizer hint 争议。

## 判断原则

- 索引可能承担定位、过滤、排序、覆盖和约束等不同职责；不能只用“是否走索引”评价价值。
- 复合索引列顺序由真实查询形状、等值/范围条件、排序分组、覆盖需求、数据分布和写入成本共同决定。
- “范围条件之后的列完全无用”并不准确：后续列可能仍参与索引条件下推、过滤或覆盖，只是未必继续缩小访问范围。
- “选择性最高的列永远放第一”也不成立。唯一点查、前缀复用、排序、范围扫描和压缩效果都可能改变结论。
- `ALL`、`Using filesort`、`Using temporary` 是调查线索，不是自动故障。小表扫描或小结果集排序可能比复杂索引路径更便宜。
- 优化器成本是估算。重点比较估算行数、真实基数、数据倾斜与运行指标，而不是只比较 cost 数字。

## 新增索引前

1. 收集查询频率、延迟贡献、参数分布、表结构、现有索引及执行计划。
2. 确认索引针对已证实瓶颈，而不是针对一次偶发样本。
3. 检查能否复用或调整现有索引，避免大量重叠前缀。
4. 评估存储、buffer pool 占用、页分裂、写放大、复制和 DDL 成本。
5. 用代表性数据与并发验证读收益及写回归；准备撤回方案。

不要为了覆盖查询把大字段机械塞入索引。覆盖收益必须与索引体积、更新频率和页利用率一起评估。

## 删除索引前

- 确认观察窗口覆盖业务周期、定时任务和低频关键路径；“最近没用”不等于“可以删”。
- 排查索引是否用于唯一约束、外键支持、锁范围控制或灾备/运维查询。
- 在版本和平台支持时，可先将候选索引设为 invisible，观察计划与性能，再决定是否物理删除。不可见索引仍会被维护，唯一性仍会生效，因此它只模拟优化器不可见，不模拟写入收益。
- 删除后的回退需要重建索引；大表重建可能代价很高，不能把它描述成瞬时回滚。

## 统计信息与计划漂移

当估算基数明显偏离数据分布时，先确认统计信息是否陈旧、采样是否代表热点值、相关列是否存在相关性。直方图可能改善部分谓词估算，但也会带来维护与版本差异；更新统计信息可能改变其他 SQL 的计划，必须观察回归面。

## Hint 与强制索引

optimizer hint 或 `FORCE INDEX` 可以作为受控诊断实验或临时缓解，但不能替代根因分析。使用前记录：适用 SQL 范围、数据分布假设、版本行为、退出条件和后续修复。数据增长后，今天正确的强制路径可能成为明天的故障源。

参考：[MySQL 8.4 Invisible Indexes](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html)、[MySQL 8.4 Optimizer Statistics](https://dev.mysql.com/doc/refman/8.4/en/optimizer-statistics.html)。
