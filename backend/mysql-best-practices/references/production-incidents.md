# 生产事故处置

用于连接耗尽、CPU/I/O/磁盘异常、复制延迟、实例不稳定和崩溃恢复。事故中先稳定服务并保存关键证据，再做根因修复；所有有副作用动作遵循现有故障指挥与授权流程。

## 通用节奏

1. 明确用户影响、开始时间、受影响节点/租户和当前变更。
2. 保存关键时间线与只读证据，避免为“清现场”先重启或清空指标。
3. 选择可逆止损：在获批前提下降低入口流量、暂停批任务、限制高成本功能或隔离异常调用方。
4. 每次动作只改变少量变量，记录时间、操作者、预期和实际效果。
5. 指标恢复后继续观察，区分临时缓解与根因修复，并补齐复盘证据。

## 连接耗尽

连接数达到上限可能由流量突增、连接池泄漏、慢 SQL、锁队列、事务未结束、连接建立风暴或实例资源不足引起。先核对活动/空闲连接、创建速率、会话年龄、来源、等待事件、线程和应用池配置。

直接提高 `max_connections` 可能增加内存、调度和下游争用，延迟真正过载点。只有证明容量充足、上游连接需求合理并有回收方案时，才将它作为临时措施。

## CPU 或 I/O 饱和

- CPU 高：区分调用量、单次成本、解析/排序、并发和后台任务；同时检查主机 steal/throttling 与平台配额。
- I/O 高：区分数据页读取、脏页刷写、redo/binlog、临时表、备份、DDL 和存储层抖动。
- buffer pool 命中率或磁盘利用率是线索，不单独证明根因；与查询、时间线和等待事件交叉验证。
- 不在事故中同时改多个全局参数。参数变更必须记录原值、作用域、持久化方式、内存上界和恢复步骤。

## 磁盘逼近上限

先识别增长来源：数据/索引、binlog/relay log、redo/undo、临时文件、错误/慢日志、备份或在线 DDL 影子对象。删除文件前确认 MySQL 与平台的生命周期管理方式，不能直接移除正在使用的数据库文件。

紧急清理也要保留恢复与审计需要。扩容只能争取时间；随后必须处理增长源、保留策略和告警窗口。

## 复制延迟

确认复制技术与拓扑，再区分 source 生成过快、网络/存储、单线程或依赖限制、大事务、DDL、冲突/错误和 replica 查询竞争。延迟指标必须结合 relay log、应用/提交进度和复制线程状态理解。

不要默认把读流量切到落后副本；先确认业务对陈旧读、读后写一致性和故障切换的容忍度。跳过复制错误、重置复制位置或重新搭建副本都需要明确的数据一致性方案。

## 崩溃与恢复

- 先保存日志、版本、启动参数、磁盘状态和最近变更；重复无目的重启可能覆盖证据并加重恢复。
- 优先使用正常崩溃恢复、已验证备份或新实例恢复，不直接修改 InnoDB 文件。
- `innodb_force_recovery` 只用于无法正常启动时的数据抢救，并在独立物理副本上从低级别开始。级别 4 及以上存在永久损坏风险；目标是尽快导出可读数据，不是让实例恢复生产服务。
- 任何故障转移都要核对数据落后量、写入隔离、防脑裂和回切条件。

参考：[MySQL 8.4 Forcing InnoDB Recovery](https://dev.mysql.com/doc/refman/8.4/en/forcing-innodb-recovery.html)、[MySQL 8.4 Replication Troubleshooting](https://dev.mysql.com/doc/refman/8.4/en/replication-problems.html)。
