# DDL 与批量数据变更

用于索引、列、约束和表结构变更，以及大批量更新、删除、回填与迁移。

## 变更前必须确认

- 精确版本、发行版与云平台限制；表大小、行数、增长率和分区情况；
- DDL 支持的算法与锁级别，是否重建表，失败时是否会退化到更昂贵算法；
- 峰值/当前写入量、长事务、元数据锁、磁盘及临时空间、redo/binlog 生成能力；
- 副本数量、复制模式、延迟容忍度和故障转移影响；
- 变更工具的节流、暂停、恢复、失败清理和最终切换机制；
- 监控指标、停止条件、值守人、业务窗口和回退/前滚方案。

MySQL 在未指定算法时可能在 `INSTANT`、`INPLACE`、`COPY` 间选择可用路径。`INSTANT` 仍可能短暂申请排他元数据锁；`INPLACE` 可能重建表并消耗大量 I/O；`COPY` 通常不允许并发 DML。不要只根据“支持 online”判断生产影响。

若目标是禁止自动退化到高成本算法，应在变更设计中明确允许的算法与锁行为，使不满足条件时失败，而不是悄悄执行更重的路径。具体语法与行为必须按目标版本官方文档核实。

许多 DDL 会触发隐式提交，不能假设放在显式事务中就能用 `ROLLBACK` 撤销。不要用关闭外键检查、唯一性检查或 binary logging 的方式掩盖数据问题；确有迁移场景需要时，必须单独证明一致性、复制和恢复影响。

## 批量 DML

批量更新、删除或回填应满足：

- 使用稳定且唯一的键做 keyset 分批，记录 checkpoint；避免依赖大 `OFFSET`；
- 每批事务足够小，可观察、可暂停，且不会长期占用锁或堆积 undo；
- 操作具备幂等、去重或可重入设计，中断后能从已确认位置继续；
- 同时观察业务延迟、锁等待、redo/binlog、磁盘、复制延迟和错误率；
- 用反馈式节流调整批大小和间隔，不使用脱离实例能力的固定“安全批量”；
- 先做只读影响评估，明确匹配范围与边界，再申请写入授权。

大事务拆批会改变原子性。若业务要求全量原子提交，不能在未说明语义变化时擅自拆分。

## 回退现实

- 许多 DDL 的回退实际是再次执行 DDL，而不是瞬时撤销；新增数据可能让旧 schema 已无法直接恢复。
- 删除列、收窄类型、清理数据和重建表可能不可逆。先使用兼容演进、双读/双写或延迟删除策略，并单独验证恢复过程。
- 备份存在不等于可恢复；高风险变更前确认恢复点、保留周期、加密密钥和最近一次恢复演练结果。
- 在线变更工具会引入触发器、影子表或额外复制流量时，要把清理与冲突风险纳入方案。

## 变更后验证

验证 schema 与预期一致、应用新旧版本兼容、错误率与延迟无回归、锁与资源恢复基线、副本追平，并检查失败遗留对象。仅看到命令成功不等于变更完成。

参考：[MySQL 8.4 `ALTER TABLE`](https://dev.mysql.com/doc/refman/8.4/en/alter-table.html)、[MySQL 8.4 Implicit Commit](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。
