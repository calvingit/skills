# 慢 SQL 与延迟异常

用于单条 SQL 变慢、整体吞吐下降、尾延迟升高或周期性抖动。目标是定位瓶颈类别，而不是看到某个执行计划字段后立即改 SQL 或索引。

## 最小证据集

优先收集以下信息；拿不到的项目明确标为未知：

- MySQL 版本、发行版、实例角色和问题时间窗口；
- SQL digest 或已脱敏语句、参数类型、调用频率、并发度和超时位置；
- 表结构、现有索引、近似行数、数据分布和最近 schema/数据量变化；
- `EXPLAIN`，必要时使用 `FORMAT=JSON`；只有满足安全条件时才用 `EXPLAIN ANALYZE`；
- 延迟分位数、执行次数、检查/返回行数、锁等待、临时表、排序和错误数；
- 同期 CPU、I/O、内存、磁盘、连接数、事务和复制指标；
- 变慢前后的发布、参数、统计信息、流量或数据倾斜变化。

若 `sys` schema 可用，可从聚合视角寻找总耗时和调用量贡献者：

```sql
SELECT query, db, exec_count, total_latency, avg_latency,
       lock_latency, rows_examined, rows_sent, tmp_disk_tables,
       full_scan, first_seen, last_seen
FROM sys.statement_analysis
LIMIT 20;
```

该视图基于 Performance Schema 聚合数据；先确认采集是否开启、计数器覆盖的时间窗口和执行权限。输出可能包含业务信息，分享前脱敏。

## 诊断顺序

1. **确认症状**：区分平均延迟、尾延迟、吞吐和超时；确认是单 digest、单租户、单节点还是全局问题。
2. **分解总成本**：总耗时约等于调用次数 × 单次耗时。先判断主要矛盾是次数暴涨，还是单次执行变慢。
3. **对照计划与数据**：检查访问路径、估算行数与实际分布、连接顺序、回表、排序、临时表和分区裁剪；不要孤立解读 `type` 或 `Extra`。
4. **排除等待放大**：锁等待、磁盘抖动、buffer pool 命中下降、连接排队和复制读取都可能表现为“SQL 慢”。
5. **定位变化点**：关注统计信息、索引可见性、参数、schema、数据倾斜、发布、流量和缓存冷热变化。
6. **最小化实验**：一次只改变一个主要变量；使用相同参数分布、并发和缓存条件做对比。

## 常见疑难点

- **隐式类型转换或字符集/排序规则转换**：可能改变索引利用方式；核对列类型、绑定参数类型与比较两侧的字符集。
- **数据倾斜与计划漂移**：平均分布不能代表热点值。核对估算与真实基数，必要时评估统计信息或直方图，而非直接固定执行计划。
- **深分页**：大 `OFFSET` 仍需扫描并丢弃大量记录。若业务语义允许，使用稳定、唯一排序键的 keyset pagination。
- **N+1 与请求放大**：单条 SQL 很快也可能因每请求执行数过高拖垮实例；从调用链与 digest 次数共同确认。
- **超大 `IN`、宽行与无界结果集**：解析、网络、序列化和应用内存也可能是瓶颈；不要只观察数据库执行时间。
- **排序和磁盘临时表**：它们是进一步调查的信号，不自动等于缺索引；核对查询语义、结果规模、行宽和内存压力。
- **冷缓存基准**：一次执行结果不能代表线上稳态；明确预热、重复次数与并发条件。

## 改动判据

任何优化建议至少说明：命中了哪个已证实瓶颈、会增加什么写放大或资源成本、如何在可比窗口验证，以及无收益或产生回归时如何撤回。优化单次延迟但显著增加总调用、锁范围或复制压力，不算完成。

参考：[MySQL 8.4 `sys.statement_analysis`](https://dev.mysql.com/doc/refman/8.4/en/sys-statement-analysis.html)、[MySQL 8.4 `EXPLAIN`](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。
