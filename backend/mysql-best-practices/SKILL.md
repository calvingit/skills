# MySQL Best Practices

面向生产环境分析 MySQL 问题和变更。核心原则是先建立证据，再区分根因；优先给出影响最小、可验证、可回退的处置方案，而不是套用固定阈值或口诀。

## Authority

按以下顺序处理冲突：

1. 用户当前任务的明确要求和授权边界；
2. 目标项目已有的数据库规范、SLO、变更流程和云平台限制；
3. 当前实例、监控、执行计划和版本信息所证明的事实；
4. MySQL 对应版本的官方文档；
5. 本 Skill 的通用经验。

项目规则与运行证据冲突时，不静默选边；指出冲突及其风险。MariaDB、Aurora MySQL、RDS、Cloud SQL、Vitess、PlanetScale 等不能默认等同于社区版 MySQL。

## Workflow

1. **确认现场**：识别版本与发行版、拓扑、环境、权限、时间窗口、表规模、负载特征，以及任务属于事故止损、根因分析还是计划变更。
2. **加载专题**：只读取与问题直接相关的 `references/` 文件，不默认加载全部内容。
3. **建立基线**：先收集只读证据；标明采样窗口和数据来源，把已证实事实、合理推断和未知项分开。
4. **划分根因**：至少区分 SQL/执行计划、锁与事务、CPU/I/O/内存/磁盘、连接池、复制链路及外部依赖，避免只盯着一条 SQL。
5. **选择处置**：优先最小、可逆的改动；说明预期收益、适用前提、副作用、验证指标、停止条件和回退方案。
6. **验证闭环**：在可比流量与采样窗口下比较变更前后数据；不能验证时明确说明，不把推测写成结论。

## Hard guardrails

- 默认只读。未经明确授权和目标确认，不执行 DDL、DML、`KILL`、`SET GLOBAL`、主从切换、重启或故障转移。
- `EXPLAIN ANALYZE` 会实际执行语句。未确认语句只读、成本可控且环境允许时，不在生产库运行。
- 不从单条 SQL 文本直接得出“加索引”或“删索引”的结论；至少结合表结构、现有索引、执行计划、数据分布和运行指标。
- 不把 `FORCE INDEX`、扩大 `max_connections`、修改全局参数、重启实例或关闭安全机制当作首选修复。
- 不使用脱离工作负载的绝对阈值，也不机械套用“最左前缀”“选择性最高列放最前”“见到全表扫描就加索引”等口诀。
- “在线 DDL”不等于无锁、无停顿或无资源消耗；必须核实版本、算法、元数据锁、磁盘空间、写入压力和复制影响。
- 诊断输出、日志和示例必须脱敏，不回显口令、连接串、令牌、个人信息或完整敏感参数。
- `innodb_force_recovery` 仅属于数据抢救的最后手段；没有独立物理副本、明确级别风险和导出方案时，不建议启用。

## Response contract

输出应让操作者能区分“现在知道什么”和“下一步会改变什么”：

1. **结论与影响**：一句话说明当前判断、影响面和紧急程度；证据不足时写“尚不能确定”。
2. **事实与证据**：列出版本、时间窗口、指标、执行计划或阻塞关系，并注明来源。
3. **假设与缺口**：按可能性或验证成本排序，不把相关性当因果。
4. **建议动作**：区分立即止损、根因修复和长期预防；高风险命令先展示影响与前置确认。
5. **验证与回退**：给出前后对比指标、观察时长、失败停止条件和回退路径。

## Boundaries

- 不代替现场 DBA、SRE 的变更审批和故障指挥权限。
- 不承诺仅凭 SQL 文本即可预测生产表现；缺少关键证据时先索取最小必要信息。
- 不为了“最佳实践”扩大当前任务范围，不无依据地重构 schema、拆库分表或引入中间件。
- 不把 MySQL 8.0/8.4 的行为直接套用于 5.7、MariaDB 或云厂商兼容实现。
