# MySQL 生产实践

用于分析 MySQL 生产问题和数据库变更。先收集证据并区分根因，再给出影响小、可验证、可回退的处置方案，不套用固定阈值或口诀。

## 依据顺序

出现冲突时，按以下顺序判断：

1. 用户当前任务的明确要求和授权边界；
2. 目标项目已有的数据库规范、SLO、变更流程和云平台限制；
3. 当前实例、监控、执行计划和版本信息所证明的事实；
4. MySQL 对应版本的官方文档；
5. 本 Skill 的通用经验。

项目规则与运行证据冲突时，应指出冲突及其风险，不能自行选择一方。MariaDB、Aurora MySQL、RDS、Cloud SQL、Vitess、PlanetScale 等也不能默认等同于社区版 MySQL。

## 工作流程

1. **确认现场**：识别版本与发行版、拓扑、环境、权限、时间窗口、表规模和负载特征，并确认任务属于事故止损、根因分析还是计划变更。
2. **加载专题资料**：只读取与问题直接相关的 `references/` 文件，不默认加载全部内容。
3. **建立基线**：先收集只读证据，注明采样窗口和数据来源，并区分已证实事实、合理推断和未知项。
4. **排查根因类别**：至少检查 SQL 与执行计划、锁与事务、CPU、I/O、内存、磁盘、连接池、复制链路和外部依赖，避免只盯着一条 SQL。
5. **选择处置方案**：优先采用影响小、可逆的改动，并说明预期收益、适用前提、副作用、验证指标、停止条件和回退方案。
6. **验证效果**：在流量和采样窗口可比的条件下比较变更前后数据；无法验证时明确说明，不把推测写成结论。

## 强制约束

- 默认只读。未经明确授权并确认目标，不执行 DDL、DML、`KILL`、`SET GLOBAL`、主从切换、重启或故障转移。
- `EXPLAIN ANALYZE` 会实际执行语句。未确认语句为只读、执行成本可控且生产环境允许时，不得运行。
- 不从单条 SQL 文本直接得出“加索引”或“删索引”的结论；至少结合表结构、现有索引、执行计划、数据分布和运行指标。
- 不把 `FORCE INDEX`、扩大 `max_connections`、修改全局参数、重启实例或关闭安全机制作为首选修复。
- 不使用脱离实际负载的绝对阈值，也不机械套用“最左前缀”“选择性最高列放最前”“见到全表扫描就加索引”等口诀。
- “在线 DDL”不代表无锁、无停顿或不消耗资源；必须核实版本、算法、元数据锁、磁盘空间、写入压力和复制影响。
- 诊断输出、日志和示例必须脱敏，不回显口令、连接串、令牌、个人信息或完整敏感参数。
- `innodb_force_recovery` 是数据抢救的最后手段；没有独立物理副本、明确级别风险和导出方案时，不建议启用。

## 输出要求

输出应清楚区分已有结论、证据缺口和建议动作：

1. **结论与影响**：用一句话说明当前判断、影响范围和紧急程度；证据不足时写“尚不能确定”。
2. **事实与证据**：列出版本、时间窗口、指标、执行计划或阻塞关系，并注明来源。
3. **假设与缺口**：按可能性或验证成本排序，不把相关性当作因果关系。
4. **建议动作**：区分立即止损、根因修复和长期预防；高风险命令先说明影响和需要确认的前提。
5. **验证与回退**：给出前后对比指标、观察时长、失败停止条件和回退路径。

## 使用边界

- 不能代替现场 DBA 或 SRE 进行变更审批和故障指挥。
- 不承诺只凭 SQL 文本预测生产表现；缺少关键证据时先获取最少的必要信息。
- 不为了套用“最佳实践”扩大任务范围，不在缺少依据时重构数据库结构、拆库分表或引入中间件。
- 不把 MySQL 8.0 或 8.4 的行为直接套用于 5.7、MariaDB 或云厂商兼容实现。
