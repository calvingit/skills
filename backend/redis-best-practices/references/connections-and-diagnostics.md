# 连接与诊断

## 客户端路径

确认客户端版本、同步或异步模型、连接池或多路复用行为；复用已有客户端，避免每次请求重建连接。阻塞命令、订阅及事务可能要求独占连接，按具体驱动核对。HTTP 服务接口不套用 TCP 连接池建议。

区分连接建立、池等待、命令执行和整体请求的超时；同时检查应用、驱动与上游重试。先确认瓶颈来自排队等待还是服务端执行，不要直接扩大连接池。pipeline 的批次要限制命令数和字节数，检查逐项失败与部分完成；重试整批可能重复写入。

## 按症状取证

| 症状 | 优先证据 |
| --- | --- |
| 应用延迟而服务器耗时低 | 池等待、网络、重连、返回体积、序列化及重试 |
| 命令耗时高 | 限定数量的 SLOWLOG 样本、命令复杂度、相关 Key 的大小与访问分布 |
| 内存或淘汰异常 | 相关 INFO memory/stats、maxmemory 策略、过期分布、缓冲区及持久化压力 |
| 热点或吞吐不均 | 分片级负载与 Key 访问分布；增加分片不一定分散单个热 Key |

SLOWLOG 不包括客户端通信耗时，没有慢日志不能排除端到端延迟。累计命中与淘汰计数需要在同一时间窗口取差值，并考虑重启或计数重置；阻塞客户端也可能是预期的阻塞读取。

`SCAN` 不是一致性快照，可能返回重复元素，COUNT 只是工作量提示。考虑扫描期间的数据变化，并限制每轮开销和整个扫描过程的资源消耗。按对象规模限制每次读取量，不把 HGETALL、SMEMBERS 一概禁止，也不把 SCAN 宣称为无成本的生产安全操作。

比较变更前后同类负载的延迟、错误、资源和吞吐，保留未验证项。禁止以“没有报错”替代性能改善证据。
