# Redis 工程实践

先确定 Redis 在当前系统中承担缓存、会话、计数、消息还是协调职责，再检查数据丢失、重复执行、过期或服务不可用时的行为是否符合业务约定。不默认增加缓存、锁或消息基础设施。

## 工作方式

1. 确认任务是实现、审查、诊断还是运行变更。读取相关调用链，确认数据以哪里为准、能否重建，以及读写和恢复分别由谁负责。
2. 核对服务端版本、发行版、部署拓扑、客户端及连接方式。Redis Open Source、托管服务、Redis Software、Valkey 和兼容接口不能默认具有相同能力；HTTP 客户端与 TCP 客户端也分别判断。
3. 根据受影响边界加载下表资料。先使用现有配置、指标、日志和限制采样量的只读检查；证据不足时说明还缺哪些必要证据，不执行全量审计。
4. 每项建议都应说明要解决的具体故障或运行限制，并区分事实、假设和待验证方案。已授权实现时做最小修改；仅诊断或审查时报告发现。
5. 用受影响行为和可比负载验证结果；报告实际检查、未验证范围、运行变更的停止条件及恢复路径。测试替身不能证明真实复制、集群或持久化行为。

## 操作边界

- 审查和诊断默认只读。服务端写入、删除、配置修改、ACL 变更、清空数据、故障转移或压测须有明确授权和已确认的目标；已有授权覆盖的操作不重复询问。
- 只读不等于低成本。限制采样数量、耗时和返回体积；生产环境不默认执行 `KEYS`、`MONITOR`、全库遍历或大集合全量读取。`SCAN` 也需限制耗时和资源消耗。
- 不清空 SLOWLOG 来收集新证据，不把 `CONFIG SET` 或重启作为默认诊断步骤。日志、Key、成员值和命令参数可能含敏感信息，输出前脱敏。
- 超时不代表写入未发生；查明执行结果或重试必须考虑该操作的重复副作用。
- 不用固定命中率、内存百分比或连接数作为通用故障结论；结合业务角色、采样窗口、负载和服务目标。
