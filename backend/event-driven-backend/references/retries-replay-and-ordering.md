# 重试、重放与顺序

## 重试与失败隔离

区分暂时不可用、确定业务拒绝、无效消息与结果未知；副作用的执行结果未知时，先按操作标识查询或读取已记录结果，按既有恢复协议继续处理；证据不足时保留“结果未知”，不要把恢复等同于重新执行副作用。核对客户端、消息代理（broker）、消费者与调度器各层重试，限制总尝试、等待时间和容量，避免立即重新入队（requeue）造成反复投递。

死信队列（DLQ）只隔离未完成工作，不代表业务完成。记录失败原因、契约版本、操作标识和恢复责任；按敏感信息及保留期要求保存。进入 DLQ、告警、人工修复和重放是不同动作。

## 重放

重放前明确选择条件、数量、时间范围、目标消费者版本、已发生的副作用、去重保留窗口和当前权限。旧消息可能在新代码下产生不同效果；先核对 API/事件契约的兼容结论。

获得授权后，优先分小批量执行，限制速率并提供停止后续投递的方式，观察业务效果、积压和依赖容量。保留原始标识及本次重放记录；不要为绕过去重默认生成新业务 ID。预演（dry-run）如果仍会触发外部写入或业务副作用，就不能声称无副作用；是否安全需检查实际调用，不能仅凭模式名称判断。

清空 DLQ、重置消费位点（offset）、批量重新投递不能当作普通诊断步骤。停止重放不能撤销已产生的付款或通知，恢复方案应说明这种限制。

## 顺序和容量

确定顺序要求针对哪个业务实体，而不是默认全局顺序。生产者的分区策略、并行消费、延迟重试、DLQ 和重放都会影响完成顺序。增加分区或消费者并发前，核对分配与历史数据是否仍满足约定。

按业务版本、状态转换或允许的补偿规则处理重复、乱序和迟到，不从事件时间戳单独推断因果顺序。无法处理的消息应明确阻塞或隔离，不能静默丢弃。

结合积压量、最早未处理消息的等待时长、到达与处理速率、失败率以及下游饱和度判断问题。增加消费者可能放大数据库或外部依赖压力；排队、预取和并发都要有资源边界。

资料：[RabbitMQ 消费者预取](https://www.rabbitmq.com/docs/consumer-prefetch)、[SQS DLQ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)。
