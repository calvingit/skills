# 副作用与验证

## 跨边界提交

数据库提交与消息发布若不在同一个原子边界，分别分析“业务提交但消息未发出”和“消息发出但业务未提交”。普通数据库事务无法自动撤销消息代理（broker）或外部接口上已经发生的操作。

outbox 可将业务状态与待发布记录纳入同一数据库事务，但消息转发进程（relay）发布成功后、标记前仍可能重复发布。采用前确认现有事务/CDC 能力、relay 恢复、操作标识、顺序、积压和清理策略；不要把 outbox 本身当成端到端一次处理保证。

inbox 或去重记录需与本地业务效果一起原子提交，或有明确的恢复状态。先标记已处理再执行，可能漏掉实际操作；先执行再单独写标记，又可能导致重复操作。数据库去重不能自动保护数据库之外的扣款或邮件。

外部副作用需要可复用的业务操作标识、供应方幂等保证或结果核对路径；补偿本身也是可能失败或重复的业务操作。缺少这些保证时，应保留“结果未知”的状态，由业务负责方决定如何恢复，不能声称已经回滚。

## 选择故障窗口验证

| 交错 | 观察重点 |
| --- | --- |
| 业务提交后发布前中断 | 消息最终能否恢复发布，业务结果是否仍一致 |
| 发布成功但确认丢失 | 重发后的重复消息是否导致重复业务效果 |
| 副作用成功但消费确认前中断 | 重新领取能否恢复结果而不重复操作 |
| 任务持有权失效后旧执行者恢复 | 新旧执行者是否破坏业务不变量 |
| 重试、乱序或历史消息重放 | 版本兼容、状态收敛、权限及已发生效果 |

使用隔离的消息代理（broker）、实际持久化边界或项目已有故障替身，记录注入点、操作标识、业务结果与确认进度。只观察队列变空、ack 成功或 mock 调用次数不足以证明业务交付正确。

替身能验证应用决策，不能证明实际消息代理的持久化、重平衡或故障转移保证。契约、配置与端到端证据分别报告；最终验收沿用调用方流程。

资料：[Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。
