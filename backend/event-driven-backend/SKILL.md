# 事件与后台任务

沿着生产者、传输设施、消费者、业务副作用和确认这条路径，检查整个流程是否正确。适用于涉及投递、异步副作用或恢复边界的任务；普通数据库操作不因此引入消息系统。

## 工作方式

1. 确认消息或任务的业务含义、完成标准、顺序范围与授权。读取真实生产、消费、重试和停止路径，识别业务操作标识、消息标识、当前执行者，以及消费分配或租约认定的持有者；正在执行不代表仍有权处理该任务。
2. 核对消息代理（broker）或服务、版本、客户端、拓扑及实际配置。分别核对消息发送、broker 接收、发布确认（publisher confirm）、持久化、消费者领取、业务提交，以及消费确认（ack）、消费位点提交（offset commit）或消息删除（delete）的保证。接收、确认和持久化不是同义词，各阶段是否存在及其先后关系以实际协议和配置为准，不能从产品名称推定保证。
3. 针对受影响阶段画出成功、中断与结果未知的时间线，找出丢失、重复、旧执行者继续写入、乱序和积压的窗口；只加载相关资料。
4. 在已授权范围内选择最小修改。outbox、inbox、事务、重试队列和租约都必须对应具体故障窗口；不默认引入新组件或声称端到端恰好一次处理（exactly-once）。
5. 验证相关交错与业务结果，记录命令、证据、实际覆盖及未验证的基础设施行为。诊断或审查不直接修改；重放、清空队列、重置消费位点（offset）、发布消息或故障注入需要对应环境及副作用的明确授权。

## 职责与边界

- 业务含义、权限、完成标准与兼容政策来自已确认需求；共享设计归项目既有设计流程。无 SPEC/HLD 时不强制创建，有这些文件时不越权改写。
- 事件字段、Schema 版本和新旧消费者兼容性由 `api-contracts` 统一检查；本 Skill 依据其结论，判断部署、处理积压和重放时会出现哪些生产者与消费者版本组合。在独立安装中同样必须核对已确认事件契约，不能因缺少另一个 Skill 而略过或阻塞其他调查。
- 具体存储、连接和集群机制复用对应数据库或官方资料；这里负责完整投递生命周期，不重复维护 Redis 或 MongoDB 手册。
- 不建立独立验收流程，不替代 `verify` 或 `debug`。只读日志、指标和隔离场景可用于分析；没有生产访问不代表必须停止所有诊断。
- 不能仅凭消息字段认定身份、租户和权限。应核对消息来源、允许的操作及执行时的权限策略，管理员或重放入口也不得自动绕过授权。
