# Terminology Zh

把英文概念转换成中国技术团队能够准确理解的表达。先保持概念边界，再处理中文是否自然；不要为了避开“翻译腔”而改掉已经稳定的技术术语。

## 职责边界

只处理术语选择、概念命名和跨文件一致性，不承担整篇文章的语气、句法或结构润色。

- 普通中文表达存在 AI 味、模板句式或翻译腔时，交给中文改写类 Skill。
- 业务概念的含义、边界或代码命名尚未确定时，先进行领域建模；本 Skill 只处理已经明确的概念如何用中文表达。
- 产品名、协议名、代码标识符、命令、路径、API 字段和引用原文默认保持不变。
- 不为“全中文”强译没有稳定译名的缩写、专有名词或社区通用英文术语。
- 不因一个标准译名看起来像直译，就改写成含义不同的日常表达。

## 语义约束

术语表提供按语境选择的候选，不是键值映射。每次替换都要确认概念含义、责任主体、技术层级和读者；同一英文词承载不同含义时分别处理。未确定语义就保留原表达并说明疑点，禁止按词表批量替换。

**术语和解释是两层内容。** 对技术受众，优先使用准确、稳定、可检索的专业术语；需要降低理解成本时，在首次出现处补充解释，而不是用解释句替换术语本身。例如可以写“水合（Hydration，客户端恢复交互能力的过程）”，不要因为“水合”不够口语就统一改成“客户端接管”。

## 判断顺序

按以下顺序决定术语：

1. 读取用户要求、目标仓库的写作规范、术语表和已有同义表达；项目已经明确约定且含义准确时，优先保持一致。
2. 确认原词在当前上下文中的实际含义、作用和受众；不要只查英汉词典，也不要仅凭字面观感判断译名是否“生硬”。
3. 有上游产品、标准、框架或权威来源的官方中文术语时，优先采用其在当前语境中的稳定译法；必要时参考官方术语库、官方中文文档和本地化风格指南。
4. 没有项目或官方约定时，优先采用目标读者已经熟悉且概念边界准确的行业译名。
5. 中文译名准确但不易理解时，首次写作“中文术语（English term）”并补充简短解释；后续沿用统一术语。
6. 没有稳定译名，或中文会丢失关键区分、影响检索时，保留英文或约定缩写，通过上下文解释其作用。
7. 只有在缺少稳定术语且直接翻译确实不自然时，才改写为能够说明作用的中文短语。

含义不确定且会改变译法时，先查原始定义、源码或官方文档；仍无法确定时列出少量候选并说明差异，不擅自定稿。

沿用准确、自然的既有约定，避免堆叠定语和生造术语。同一概念统一表达，不同概念保留专业区分。不要把相近概念合并成更口语但更宽泛的说法，例如不要把 first-class 简化成“原生支持”，也不要把 grounding 泛化成“事实校准”。

## 本地化原则

参考成熟本地化指南时，吸收其决策原则，不把某一厂商的产品术语机械套用到所有项目。

- 面向技术读者时，稳定术语通常优先于解释性意译。
- 面向普通用户的 UI 文案可以更生活化，但不能改变操作含义、状态和风险级别。
- 同一概念保持一致译名；不同概念即使中文接近，也要保留必要区分。
- 产品或上游已有批准译名时，优先沿用；项目有更高优先级的明确约定时遵循项目约定。
- 术语首次出现可补英文以便检索，后续无需重复中英并列。
- 不逐词翻译复合术语；先识别完整概念，再决定中文表达。

## 典型改法

这些示例用于说明判断方式，不是脱离上下文的固定词典，也不得作为批量替换规则使用。

批量审校常见的架构、工程、交付和 Agent 术语时，读取 [常用技术术语参考](references/common-terms.md)。参考表只提供语境化候选，不能覆盖当前项目已有的准确约定，更不能作为键值映射执行替换。

| 原表达 | 推荐表达 | 判断依据 |
| --- | --- | --- |
| 条件式 high-level-design | 按需概要设计 | 这里表达的是“满足条件时才进入”的流程行为，不存在必须保留的 conditional 专业术语 |
| capability owner | 能力维护者 / 负责该能力的组件 | 根据语境区分人员职责与组件职责，不固定翻成“能力所有者” |
| first-class support | 一等支持 / 作为一级能力支持；必要时保留 first-class | first-class 描述语言或系统中的地位，不应直接替换成语义不同的“原生支持” |
| source claim | 资料中的观点 / 来源中的说法 | 这是组合表达而非稳定技术术语，可按上下文自然改写 |

## 执行流程

1. 确定审校范围和权威来源，识别必须保持原样的代码、字段、专名与引用。
2. 搜索候选术语及其变体，至少检查标题、正文、表格、链接文字、注释、提示词和 UI 文案。
3. 为每个候选恢复原始概念，判断问题属于误译、硬翻译、含义过宽、含义过窄还是前后不一致。
4. 检查项目约定、上游官方译名和行业通用译名，区分“标准术语”和“帮助理解的解释”。
5. 按判断顺序选择推荐表达；必要时先给用户少量候选，不提供无差别的同义词列表。
6. 修改所有承载同一概念的文本。禁止盲目全局替换，必须逐处确认语义。
7. 回查旧表达和中英混用残留，确认没有改动代码标识符或破坏原意。
8. 确认专业区分、事实强弱和责任主体未变，中文表达清楚，受保护内容完整，再运行目标仓库已有的轻量检查并报告无法验证的部分。

## 多载体一致性

术语可能同时存在于 Markdown、YAML、HTML、SVG、流程图源文件、图片替代文本和截图说明中。修改时：

- 使用搜索确认同一术语出现在哪些载体。
- 有可生成的图示源文件时，修改源文件并按仓库流程重新生成产物。
- 没有生成流程时，同步修改可编辑的 SVG、HTML 和周边说明。
- 二进制图片中的文字无法安全修改时，明确列为未处理项，不假装已经同步。
- 修改后再次搜索旧术语，并检查链接、转义、布局和渲染是否受影响。

## 输出

用户要求直接修改时，完成修改后只说明：

- 采用了哪些关键术语及理由。
- 修改了哪些文件或载体。
- 使用什么方式验证，以及是否仍有未处理项。

用户只要求审查时，按“原表达 / 问题 / 推荐表达 / 理由”列出有实质影响的条目，不罗列无关的个人风格偏好。
