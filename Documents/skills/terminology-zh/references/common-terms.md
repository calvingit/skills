# 常用技术术语参考

这是一组审校候选，不是固定词典。先确认概念和语境，再选择译名；项目已有准确约定时沿用项目约定。

本表采用“**稳定术语优先，解释按需补充**”的原则：技术读者已经普遍使用的中文术语，不因为看起来像直译就主动改写；解释性中文用于帮助理解，不能替代或改变原术语的概念边界。

## 架构与文档

| 英文术语或表达 | 推荐表达 | 语境说明 |
| --- | --- | --- |
| single source of truth | 唯一依据 / 权威来源 | 更强调“哪个来源最终说了算”时可使用解释性表达；不必固定翻成“唯一事实来源” |
| requirement authority | 需求权威来源 / 最终需求依据 | 项目自定义概念，强调哪一来源对需求有最终决定权 |
| ownership | 职责归属 / 维护责任 / 所有权 | 工程职责语境优先前两者；法律、资产或资源归属语境使用“所有权” |
| owner | 维护者 / 负责人 / 所有者 | 根据人员职责、资源归属或代码所有权语境选择，不固定成单一译法 |
| contract | 契约 / 接口约定 / 需求约束 | API contract、design contract 等技术语境可保留“契约”；面向一般读者时按具体含义展开 |
| concern | 关注点 / 职责 / 问题 | separation of concerns 通常译为“关注点分离”；只有明确讨论职责划分时才使用“职责” |
| boundary | 边界 / 职责边界 | 已有自然译法，不必为了避免抽象词而展开 |
| surface area | 接口范围 / 暴露范围 / 影响范围 | API surface area 常指对外暴露接口范围；不要机械译为“表面积” |
| seam | 接缝 / 可替换边界 / 测试切入点 | 测试设计中的 seam 是稳定概念；首次出现可保留英文并解释 |
| primitive | 原语 / 基础构件 / 基础能力 | 编程语言、并发、密码学等语境优先“原语”；泛指构建块时再按实际含义解释 |
| first-class | 一等 / 一级概念 / first-class | first-class function、first-class citizen 等表达描述系统中的地位；不要直接替换成“原生支持”或“核心能力” |
| opinionated | 有明确主张 / 约定较强 / opinionated | 不默认翻成“限制较多”，后者额外引入负面判断 |
| ergonomics | 易用性 / 开发体验 / API 使用体验 | 软件和 API 语境通常讨论使用体验；需要时说明具体是调用、配置还是交互体验 |
| artifact | 制品 / 产物 / 构建产物 / 交付物 | CI/CD、制品库、构建系统语境可直接使用“制品”；其他语境按产物类型选择 |
| consumer | 消费者 / 使用方 / 调用方 | 消息系统中“消费者”是稳定术语；API 或模块依赖关系可用“使用方”“调用方” |
| producer | 生产者 / 提供方 / 生成方 | 消息系统中“生产者”是稳定术语；其他语境按职责选择 |
| gate | 门禁 / 准入条件 / 判定条件 / 审批节点 | quality gate 可译“质量门禁”；自动判断、人工审批或流程进入条件要分别处理 |
| execution graph | 执行图 / 任务依赖图 | graph 本身是重要结构时保留“图”；只强调依赖关系时可写“任务依赖图” |
| frontier | 前沿 / 边界集 / 当前可执行任务 / 待解决问题 | 调度、图搜索和探索语境含义不同，不能固定翻译 |
| source of truth drift | 权威来源与实际状态不一致 | 不是稳定单一术语时，直接说明失配关系比生造“事实源漂移”更清楚 |

## 实现与 API 设计

| 英文术语或表达 | 推荐表达 | 语境说明 |
| --- | --- | --- |
| boilerplate | 样板代码 / 模板代码 / 重复样板代码 | “样板代码”是常用技术表达；需要强调机械生成或重复时再展开 |
| plumbing | 胶水代码 / 基础连接代码 | 没有统一固定译名，按语气和具体职责选择 |
| escape hatch | 逃生口 / 特殊处理入口 / 绕过机制 | 框架文档中可保留 escape hatch；中文解释应说明它允许绕过什么限制 |
| footgun | 容易误用的设计 / 高风险用法 | 中文没有统一稳定译名，直接说明风险通常更准确 |
| happy path | 正常路径 / 主流程 | “正常路径”比“快乐路径”更符合中文工程语境 |
| edge case | 边界情况 / 边缘情况 | 不等同于“少见异常”；它可能是合法输入或状态，只是处于边界 |
| fallback | 回退 / 后备方案 / 备用方案 | fallback 不一定由失败触发，也不等同于“降级”；按触发条件和行为选择 |
| best effort | 尽力而为 / 尽力执行 / 不保证成功 | 技术协议语境可用“尽力而为”；涉及承诺时应明确不保证的部分 |
| breaking change | 不兼容变更 / 破坏性变更 | 两者都常见；强调兼容性后果时优先“不兼容变更” |
| deprecation | 弃用 | 与删除、停用、不可用区分 |
| backward compatibility | 向后兼容 | 已有稳定译名 |
| graceful shutdown | 优雅关闭 / 正常关闭 | 指停止接收新工作、完成或处理存量并释放资源的受控关闭；不要仅凭字面改成“平滑关闭” |
| graceful degradation | 优雅降级 / 功能降级 | 指局部失败时保留部分能力；必要时说明具体保留和损失的功能 |
| hot path | 热路径 / 性能关键路径 | 性能工程语境“热路径”是稳定表达；面向非专业读者可补充“性能关键路径” |
| blast radius | 影响范围 / 故障影响范围 | 重点是一次变更或故障能波及多大范围，不必强行保留军事隐喻 |
| rollout | 推出 / 逐步启用 / 分批发布 | 根据功能开关、配置、版本发布等实际行为选择 |
| rollback | 回滚 | 已有稳定译名 |
| canary release | 金丝雀发布 / 小范围试发布 | 技术读者优先稳定术语；面向一般读者可在首次出现时解释 |
| dogfooding | 内部试用 / 自用验证 / dogfooding | 中文没有统一正式译名；“吃狗粮”只适合明确的口语语境 |
| headless component | 无头组件（Headless Component） | 核心是逻辑、状态、可访问性等与具体视觉表现解耦，不等于“无预设样式” |
| hydration | 水合 / 客户端水合（Hydration） | Web 框架中的稳定术语；可补充“客户端恢复交互能力”等解释，但不要用解释替代术语 |
| tree shaking | Tree Shaking / 移除未使用代码 | 生态内通常直接保留英文；解释其效果即可，不造“摇树优化”等译名 |
| eject | 弹出配置 / 脱离默认配置 / 导出底层配置 | 必须按具体工具的 eject 行为判断，不泛化成统一含义 |

## 系统与交付

| 英文术语或表达 | 推荐表达 | 语境说明 |
| --- | --- | --- |
| trade-off | 取舍 / 权衡 | 两者都是自然译法；讨论多目标之间的平衡时“权衡”更准确 |
| resilience | 复原能力 / 韧性 / 弹性 | 分布式系统、云架构和组织语境含义可能不同；“容错与恢复能力”可以解释，但不应假定它覆盖全部 resilience |
| backpressure | 背压 | 已有稳定译名 |
| eventual consistency | 最终一致性 | 已有稳定译名 |
| idempotency | 幂等性 | 已有稳定译名 |
| observability | 可观测性 | 已有稳定译名 |
| circuit breaker | 熔断 / 断路器 | 软件架构中“熔断”更常见；具体模式名可写“断路器模式” |
| fan-out | 扇出 / 并行分发 | 分布式、消息和拓扑语境可直接使用“扇出”；面向一般读者再解释行为 |
| drain | 排空 / 停止接收新任务并等待存量完成 | 进程退出、连接迁移、队列或流量切换的具体行为不同，先确认被排空的对象 |
| shadow traffic | 影子流量 / 镜像流量 | 通常指复制真实流量用于验证且不影响真实结果；首次出现可补充用途 |
| cold start | 冷启动 | 已有稳定译名 |
| zero-downtime deployment | 零停机部署 / 无停机发布 | 根据部署或发布语境选择；不要因为“零宕机”不自然就改变含义 |
| migration window | 迁移窗口 / 迁移时段 | “窗口”本身是稳定工程表达，面向普通读者可用“时段” |
| maintenance burden | 维护负担 / 维护成本 | 根据强调人力、复杂度还是长期成本选择 |
| operational overhead | 运维开销 / 运维成本 / 额外操作成本 | overhead 可指人力、资源或复杂度，不固定成单一成本类型 |

## Agent 与 AI 工程

| 英文术语或表达 | 推荐表达 | 语境说明 |
| --- | --- | --- |
| agentic | Agent 驱动 / Agent 自主执行 / agentic | 目前中文尚未形成完全统一译名；不要为了中文化固定造“智能体式”等表达 |
| autonomy | 自主性 / 自主程度 / 自主执行范围 | 讨论抽象属性时可用“自主性”，讨论权限边界时应说明允许系统自行决定什么 |
| grounding | Grounding / 基于资料或上下文生成 / 事实依据 | grounding 强调把生成建立在给定资料、上下文或外部事实之上，不等同于“事实校准” |
| guardrail | 护栏 / 防护措施 / 行为约束 / 安全边界 | “护栏”已广泛用于 AI 安全和治理语境；具体实现仍应说明约束目标 |
| human in the loop | 人在环路 / 人工参与环节 / 需要人工确认 | 技术文献可使用“人在环路（HITL）”；产品流程文案通常直接说明人工何时介入 |
| approval gate | 审批门禁 / 审批节点 / 需确认的步骤 | 正式审批、普通确认和自动准入不是同一概念 |
| elicitation | 信息采集 / 补充询问 / Elicitation | MCP 等特定规范中优先跟随规范自身术语；一般交互按目的描述 |
| handoff | 交接 / 转交 | 人、Agent、服务之间的 handoff 行为不同，按责任转移方式选择 |
| checkpoint | 检查点 | 已有稳定技术含义；如果只是普通阶段记录，不要因为形式相似就都叫 checkpoint |
| orchestration | 编排 / 调度 | 多组件、多步骤协作通常用“编排”；任务分配和资源安排更接近“调度” |
| routing | 路由 / 分流 | 请求转发用“路由”，分类派发或客服场景可用“分流” |
| tool schema | 工具 Schema / 工具定义 | Schema 可能覆盖名称、描述、参数和结构约束，不应一律缩窄成“工具参数定义” |
| tool calling | 工具调用 | 已有稳定译名 |
| context compaction | 上下文压缩 | 已有自然译法；如具体机制不是压缩而是摘要或裁剪，应按实现说明 |
| memory | 记忆 / 会话记忆 / 长期记忆 / 持久化记录 | 先区分产品记忆、模型上下文和外部存储，不要把所有持久化状态都叫 memory |
| capability | 能力 / 功能 | 根据系统抽象层次选择，不需要为了专业感固定保留英文 |
| trace | Trace / 追踪信息 / 执行轨迹 / 调用链 | 可观测性语境中的 trace 是稳定术语；审计或 Agent 轨迹语境按实际结构选择 |
| agent runtime | Agent Runtime / Agent 运行时 / Agent 运行环境 | Runtime 是产品或架构层概念时可保留英文；“运行时”和“运行环境”含义并不完全相同 |
| prompt injection | 提示词注入 / 提示词注入攻击 | 描述攻击类型时可补“攻击”；描述技术现象或防护类别时不必强加 |

## 通常保留的英文

以下内容通常不需要强行中文化：

- 产品名、框架名、协议名和标准缩写，如 Flutter、React、HTTP、MCP。
- 代码中的类名、函数名、字段名、配置项、命令和文件路径。
- API、SDK、CLI、Agent、Runtime、Token、Prompt、Schema 等中国技术团队普遍直接使用的词；有稳定中文术语或面向非技术读者时再按语境处理。
- 尚未形成稳定中文译名、且翻译会损失检索能力或概念区分的新术语。首次使用可写“中文说明（English term）”，后续沿用约定名称。

保留英文不等于中英混排越多越好。英文只是名词时，仍应使用自然中文句法组织整句。

## 句式与工程判断示例

| 原表达 | 推荐表达 | 判断依据 |
| --- | --- | --- |
| 跨局部技术契约 | 多处实现共同遵守的设计约定 | 这里不是必须保留的稳定术语，直接说明约束范围和作用更清楚 |
| Breadth / Depth | 广度 / 深度 | 中文已有准确、对称且易懂的对应词 |
| execution frontier | 当前可执行任务 / 执行前沿 | 调度语境可直接说明实际作用；图搜索等算法语境不能一律改成“当前可执行任务” |
| target test | 针对性测试 / 相关测试 | 表达“针对本次改动选择测试”的含义，不机械翻成“目标测试” |
| scope error | 适用范围错误 / 范围判断错误 / 作用域错误 | 规则语境中的 scope 多指适用范围，编程语言语境则可能确实是“作用域” |
| resident context / always-on context | 常驻上下文 / 长期保留在上下文中的信息 | “常驻上下文”在技术说明中可以使用；需要解释行为时再展开 |
| duplicated state | 重复状态 / 重复维护同一状态 | 如果问题是多处维护同一事实，后者更准确；不要一律排斥简短技术表达 |
| 实现很丑 | 实现存在代码质量或设计问题 | 不用主观感受代替工程判断；能进一步明确时应指出具体问题 |
| 表达很硬 | 表达不符合常用中文技术语境 / 存在明显翻译腔 | 直接描述语言问题，不使用含义模糊的感受性评价 |
| 方案很重 | 方案引入了不必要的复杂度 / 实施成本较高 | 说明复杂度或成本来源，不用“重”代替判断 |
| 代码很乱 | 职责边界不清 / 结构缺乏一致性 / 修改影响范围难以判断 | 根据实际问题选择具体描述，不把多种问题压成“乱” |
