# 后端 Skills 行为评估

用于维护 Skills 时评估决策质量，不是日常后端任务的必经检查。以下是可复用场景，尚未执行行为对比，不能据此声称 Skill 已改善实际效果。

## 运行方式

选择与本次 Skill 修改相关的场景，准备可运行的隔离仓库或脱敏证据。固定任务、初始文件、模型、工具和权限，分别在无该 Skill 与加载该 Skill 的新上下文中执行。已有通用工程指令保持一致；记录实际加载的技能，避免基线通过自动路由意外加载待测 Skill。

给执行者任务和原始材料，不提供下面的判定要点。只读场景不授予写入权限，外部系统使用本地替身，不连接生产。比较原始报告、文件差异和运行结果；同一条件下有多次样本时保留差异，不用一次通过证明稳定有效。

## 场景

| 场景与任务 | 最少原始材料 | 评估者判定要点 |
| --- | --- | --- |
| 普通 CRUD：沿用现有接口增加一个查询筛选项 | 路由、授权、查询实现、分页约定及现有测试 | 保留授权和结果上限；改动与需求对应；没有无依据地增加缓存、中间件或架构层次 |
| 外部写入超时：修复偶发重复扣减 | 本地 provider 替身在提交效果后丢弃首次响应，提供已有操作标识及查询接口 | 没有把超时等同于未执行；重试保留操作身份；最终业务效果和返回结果均可核对 |
| 并发状态更新：修复两个请求同时领取同一资源 | 真实持久化边界、唯一领取约束、可控制的并发入口 | 两个请求竞争时仍满足约束；没有只做先查后写或仅靠单进程锁掩盖跨实例问题 |
| 回填中断：让现有脚本安全续跑 | 分批脚本、旧数据、新业务写入入口及可注入中断点 | 检查点不越过未提交数据；重复批次不破坏结果；中途的新写入没有被覆盖或遗漏；说明旧版本能否读取新数据 |
| Worker 退出：修复部署期间丢失任务 | 消费者、确认时机、重投配置和终止窗口 | 停止领取、完成或回收在途任务的行为可观察；不把进程退出当作任务成功；检查副作用与确认之间的故障窗口 |
| 依赖变慢：分析排队与重试造成的请求堆积 | 有限连接池、队列配置、嵌套重试设置及本地延迟替身 | 能联系并发、队列和重试总量；没有直接扩大连接数或无限排队；区分证据与容量假设 |
| MySQL 局部诊断：仅分析一条查询为何变慢 | 版本、表与索引、计划、数据分布及同窗口指标 | 保持只读；从相关证据开始，证据不足时才扩大调查；没有从 SQL 文本直接建议加索引或执行变更 |

## Redis 与 MongoDB 专项场景

沿用上面的隔离、授权和对照要求；专项场景不要求真实生产权限。

| 场景与任务 | 最少原始材料 | 评估者判定要点 |
| --- | --- | --- |
| Redis 缓存回填竞争 | 源数据写入、缓存删除与旧读取回填的可控交错 | 识别旧值重新进入缓存的窗口，按业务陈旧容忍判断，不默认增加分布式锁 |
| Redis 租约过期后旧 Worker 恢复 | 获取与释放代码、外部写入、租约和暂停时间线 | 区分租约期限与执行停止；不无条件删除新所有者的锁；延长 TTL 不能替代旧写入保护 |
| Redis Cluster 批处理审查 | 客户端版本、非事务 pipeline、不同槽的独立命令 | 不把 pipeline 一律当同槽事务，不为所有 Key 使用同一 hash tag；说明客户端能力与部分完成语义 |
| Redis 延迟诊断 | 应用延迟、池等待、有界 SLOWLOG 与负载窗口 | 无慢日志不代表无延迟；不清空日志、不默认 MONITOR 或全库扫描；不凭固定阈值下结论 |
| MongoDB 缺证据的慢查询 | 查询与局部统计，缺少索引和分布，无 MCP/Atlas | 继续基于已有证据分析，列出最少缺口；索引是候选而非已验证修复，不要求先配置云服务 |
| MongoDB 事务重试与外部效果 | 事务回调中的外部写入、超时和应用重试代码 | 区分提交结果未知与确定失败；不把事务回调重放视为外部效果幂等 |
| MongoDB TTL 与结构迁移 | TTL、授权判断、旧文档、验证器及并发回填 | 不依赖及时物理删除保证业务过期；回填不覆盖新写入；验证器不等于历史数据清洗 |

## API 契约与事件交付场景

以下场景用于两个新 Skill 的维护；沿用隔离环境、固定输入和独立判定方式。

| 场景与任务 | 最少原始材料 | 评估者判定要点 |
| --- | --- | --- |
| API 字段与枚举演进 | 旧客户端解码逻辑、新旧 Schema、服务序列化与发布顺序 | 区分请求/响应方向；新增枚举不自动兼容；单位变化是行为变化；default 不保证自动填值 |
| 生成代码与契约不一致 | 权威来源、生成命令、新生成客户端和旧调用方样本 | 不直接手改生成文件；不从当前代码反推需求；新客户端通过不证明旧客户端兼容 |
| 事件 Schema 与历史消息 | 新旧消费者、历史载荷、Registry 配置、积压与回滚窗口 | 契约兼容由 api-contracts 判断，事件 Skill 检查实际版本相遇与重放；Registry 通过不证明业务效果不变 |
| 发布/消费确认丢失 | 数据库、relay、外部付款和 ack 的可控中断点 | outbox 不保证无重复发布；付款成功后未 ack 仍可能重投；操作身份与外部结果需恢复 |
| 租约到期与 DLQ 重放 | visibility、工作耗时、旧 worker 行为、DLQ 范围与业务 ID | 延长时间不替代所有权保护；重放不默认换业务 ID，不未经授权批量投递 |
| Webhook 接纳与响应 | 原始签名载荷、响应期限、持久化及后台处理顺序 | 不把签名等同于授权或去重；成功响应对应已确认接纳边界，不能仅留在内存 |

## 中文语义复核

本轮重新阅读四个 Skill 的 19 份正文与参考资料和 4 份界面配置，按主体、条件、约束强度和保证范围核对。它们是参考英文资料独立编写的本地规则，不是四份英文原稿的逐句译文。

已修正的实质问题包括：Schema Registry 的版本兼容检查不能写成实际消息校验；unbounded 表示缺少明确上界，不是数学意义的无限；正在执行不等于仍持有消费分配或租约；消息接收、发布确认、持久化和消费确认需分别判断；未知结果恢复不等于重新执行副作用；停止重放指停止后续投递，不能承诺立即终止在途效果。另补充了 MongoDB read/write concern 的区分，以及 pipelining 与客户端事务 API 的区别，并保留英文术语供查证。

依据包括 Confluent Schema Registry 兼容文档、RabbitMQ 确认协议、SQS visibility timeout、MongoDB read/write concern 与无界数组文档，以及 redis-py pipeline 文档，链接已放入对应专题。

结论：保留中文主体和关键英文术语，无需整体改为英文。问题可通过恢复专业区分和明确前提修正，没有证据表明必须换语言；也没有做同模型、同任务的中英文对照，不能声称中文与英文有完全相同的执行效果。此前文本试评不替代本轮修改后的运行验证。
