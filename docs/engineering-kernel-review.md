## 输入与方法

复核基于三份静态审计产物（规则级静态审计报告及其台账、Kernel 提案、迁移建议），并以冻结基线的源文件为准回到原句核对。审计固定了 181 个文件（engineering/ 的 26 个 Skill 及引用、脚本、schema、元数据与测试，另含 AGENTS、项目验证说明与 docs），逐文件按 Git blob 校验一致；本记录不重复其文件盘点，只记录语义复核的判断与去向。

复核操作对每条候选规则回答三件事：

1. **恢复条件与责任主体**——写明"何时、谁、必须或不得做什么"；排除解释、示例与模板占位。审计已排除的 348 个说明、历史与示例出现项不进入本复核。
2. **拆分原则与实现方法**——原则进 Kernel，方法留在 Skill / Skill 级方法，协议细节留在 Tooling（脚本、schema、CLI）。
3. **区分归属与有效性**——METHOD 未入选不等于删除，RUNTIME 归属不代表过时；无替代能力证据或对照证据不判 OBSOLETE。审计未确证任何 OBSOLETE 条目，本复核维持该结论。

## 逐族三件事复核

### Scope（K01–K02）

- **条件与主体**：范围由用户确认的需求与任务契约确立（`to-spec` 维护快照）；执行期间所有角色受其约束；发现范围外必要改动时报告而非纳入，未决选择交回 `grilling`/`to-spec`。既有改动的保护适用于任何接管、恢复与并行场景，主体是即将写入的角色。
- **拆分**：边界（不越权扩张、不吞并他人改动）进 Kernel；"记基线、列 excluded 改动、保护既有编辑"等操作方法留在 implement / quick-implement / loop 的 attempt 记录流程；具体字段（`existing_changes`、`baseline`）属 Tooling（ticket-schema、lifecycle.py）。
- **归属与有效性**：各入口重复出现的范围表述是同一不变量的角色化表达（如 R0358 对 K13 的关系），保留各自适用条件，不删角色执行检查。

### Knowledge（K03–K05）

- **条件与主体**：任何报告、验收与交接的主体都必须区分事实/推断/未知；版本匹配的查证主体是使用该资料回答问题的一方（find-docs、why、how 各自承担）；派生记录（decisions、术语、ADR、交接摘要）的维护主体是其所属 Skill，须指向权威来源。
- **拆分**：K03–K05 的边界进 Kernel；版本查证方法（context7 检索、官方来源定位）留在 find-docs 及其 references；"术语/ADR 记录"是用户已采纳的持久化行为（grilling + domain-modeling），不在本轮删除范围。
- **归属与有效性**：来源冲突未解决时不得默认一方为事实——该边界对 SPEC/HLD/Profile/示例均适用；项目特有事实归 PROJECT（Profile），不因出现在通用 Skill 中而改变归属。

### Decision（K06–K07）

- **条件与主体**：会改变需求、公共契约、兼容性、权限或验收语义的未决选择，主体是有权决定的人（用户或其确认的上游 owner：to-spec / high-level-design / to-tickets）；局部实现细节归实现角色。变更后重核派生结果的责任在变更执行方；未受影响的有效结论保留，不因流程重启作废。
- **拆分**：边界进 Kernel；"路由到谁"的规则留在 task-contract 六边界与 workflow-policy；SPEC/HLD 的修订流程与 amendment 字段属各 Skill 及 Tooling。
- **归属与有效性**：Loop 中"contract change 交回上游"与 implement 中"HLD 缺口停止实现"是同一不变量在不同停止点的表达，均保留。

### Action（K08–K12）

- **条件与主体**：授权来自用户的实际授予，不由任务、工具或交接记录的存在扩大；委派（Manager→worker、Skill→Skill）只可收窄不可扩大。资源边界（写入、清理、隔离资源）的主体是执行该操作的角色；接管重叠写入前确认原写入者停止的主体是接管方；外部写入结果未知时先查明结果再重试的主体是发起写入的一方。
- **拆分**：边界进 Kernel；资源隔离、停写确认的工程语义留在 loop / delegation / shared；worker 创建、等待、中断、会话接续的机制归 Runtime（docs/loop-runtime.md）；写锁与事务恢复的实现在 shared/store、recovery（TOOLING）。
- **归属与有效性**：K11/K12 的机制部分已正确分层（Skill 保留接管条件，Runtime 保留生命周期，脚本保留事务）——审计 MOVE_RUNTIME 条目在此层正确的，含义是保留原层，不要求搬迁。不因 Runtime 原生能力存在即视为已执行或已加载。

### Evidence（K13–K17）

- **条件与主体**：完成声明由做出声明的角色负责并与证据相称；预期独立性的责任在构造预期的角色（TDD 构造 oracle、verify 核对期望来源、test-audit 检查独有保护）；证据关联候选/环境/执行者/覆盖的责任是使用该证据做判断的一方；条件变化后重判适用性的主体是当前判断者。
- **拆分**：声明边界进 Kernel；oracle 构造方法留在 tdd，逐 AC 判断留在 verify，独有保护比较留在 test-audit，改动风险审查留在 code-review，完成状态接受留在 Loop；指纹、attempt、事务校验、快照留在状态脚本（TOOLING）。
- **归属与有效性**：文件指纹不能检测外部环境变化，事务回滚不撤销外部业务效果——工具能力边界如实保留，不据 schema 字段齐全认定证据真实。

## 四种判断共同落实同一不变量，责任不同

以下检查在不同角色重复出现同一不变量族，**不得作为重复一律删除**：

| 判断 | 落实的不变量 | 责任 | 不可合并的理由 |
| --- | --- | --- | --- |
| implement 开发自检 | K13、K15（局部） | 实现者对本 slice 的本地检查 | 提供开发者视角的即时反馈，明知其非独立证据 |
| verify 逐 AC 验收 | K13、K14、K15、K17 | 独立验收角色对每条 AC 出 PASS/FAIL/NOT VERIFIED | 预期来源独立性与证据可信度判断，不重复实现者的测试策略 |
| code-review 风险审查 | K15、K16 | 独立审查角色对改动集的缺陷/回归/复杂度 | 覆盖验收之外的风险维度，报告原文由调用方消费 |
| Loop 接受完成状态 | K13、K16、K17 | Manager 对完成/交付的接受判断 | 核对原始证据并决定状态流转，是接受语义而非再次验收 |
| tdd 行为反馈 | K14（oracle 构造） | 实现中的红绿循环 | 提供独立于实现输出的预期来源 |
| test-audit 独有保护比较 | K14、K15 | 测试价值审计 | 删除/合并测试前确认独有保护与失败模式覆盖 |

合并的对象只是原则性重述的文字；各角色的执行检查、停止点与产物要求原位保留。

## Kernel 重新确认结论

17 条不变量全部确认，表述与冻结基线一致，未新增、未改写、未删除。使用边界维持原文：Kernel 不能代替项目契约、角色写入边界或强制门禁；改变既有门禁或工作方式属于行为变更，不能作为文字去重实施。

## 剩余缺口

1. 真实 Runtime 加载、独立安装时 Kernel 的可发现性未演练；本轮以 AGENTS 与职责文档的入口链接保证仓库内可发现，Skill 级文件不依赖 Kernel 链接，独立安装不受影响。
2. 固定收尾角色与按风险选择角色的对照（漏检率、错误结论率、耗时、成本）尚无数据，实验协议另行定义；在此之前 quick-implement 与 Loop 的既有要求不变。
3. 3766 个 METHOD 出现项的逐条再复核未声称完成；后续任何迁移按迁移建议的约束执行：以台账 ID 回到源段落，保留跨句条件、角色方法与工具前提，先证实冲突已消除，再减少原则性重述。
