# Engineering Skills 职责与边界

维护现有 Engineering Skills 的职责划分、产物写入范围和结论依据。暂不新增全局 Skill、通用编排层或 Runtime，优先组合已有能力和项目方法。项目本地验证入口属于项目知识，不等于增加全局 Skill。恢复新增前，需以真实任务说明现有职责无法承接的能力缺口。

## 任务契约与六类边界

任务契约统一描述目标、范围、验收条件、决策边界和证据要求，并按需明确授权与恢复条件。它是逻辑模型，这些信息可以保留在会话或已有 SPEC / ACCEPTANCE / HLD / tickets 中，无需新建契约文件。执行、继承与变更规则见[任务契约（Task Contract）](../engineering/shared/task-contract.md)，各 Skill 无需重复这些定义。

## 事实与产物归属

每项事实只维护一个当前权威来源。引用、派生的交付条件和历史快照可以有多份，但须能追溯来源及版本，不能自行改变原意。下表分别列出规范、持久化工程状态、原始观察和 Runtime 执行状态的维护责任。

| 事实 | 权威来源 | 写入责任 | 下游使用方式 |
| --- | --- | --- | --- |
| 需求、目标、任务范围、SPEC AC | 简单任务使用经确认的会话内容，保存为文档后，以 SPEC 中的工程需求快照为准 | 用户确认需求选择，由 `to-spec` 维护快照 | HLD、tickets、实现与验收引用当前快照，新输入改变快照时先修订 SPEC。 |
| 独立维护版本的验收场景与证据规则 | 按需建立的 ACCEPTANCE | `to-spec` | 场景引用 SPEC R / AC，不再维护另一份同名 AC 定义，与 SPEC 有冲突时，停止受影响的工作并交回负责方。 |
| 交付共享技术设计 | 交付设计以 HLD 为准，长期项目决策由已有架构文档 / ADR 维护 | 交付设计由 `high-level-design` 维护，长期记录由项目约定的负责方和 `domain-modeling` 维护 | 引用 D ID 或项目来源，HLD 不自行取代长期约束，也不反向修改需求。 |
| 交付拆分、依赖、本地 AC 与约束 | `tickets/*.json` 的契约字段 | `to-tickets` 通过 create / reconcile 命令 | 通过 `covers` 与 D 引用追溯上游，本地 AC 细化本次交付，其 ID 与 SPEC AC 分属不同命名空间。 |
| ticket 生命周期、当前执行尝试（attempt）、已接受证据及执行阻塞 | ticket 的 lifecycle / execution | `loop` 通过状态命令 | frontier 返回的 ready / blocked 状态由计算得出，不另建持久化进度表，worker 只返回原始结果。 |
| 最终交付候选与状态 | `.loop/delivery.json` | `loop` 通过 delivery 命令 | 查询当前快照，并将原始报告保留在 `.loop/`，不以摘要替换报告。 |
| 项目稳定工程知识与导航 | 使用已有项目指令、术语表和架构资料，通过 Profile 定位来源 | 项目资料由各自的维护者负责，`project-setup` 维护 Profile | 按需引用，不把当前任务、运行结果或授权复制进 Profile。 |
| 可执行验证方法与能力范围 | 现有项目脚本 / CI / 本地验证 Skill | 项目工具由其维护者负责，`verification-setup` 维护方法与导航摘要 | Profile 只提供链接和摘要，方法说明不成为需求来源，冒烟检查记录也不作为当前任务已通过验收的依据。 |
| 当前候选的实际观察与审查结论 | 原执行者的命令记录、产物、verify / review 原文 | 实现者、验证者与审查者分别记录，由调用方判断适用性 | 状态脚本保存接受的事实，不解析报告、证明真实性或认证独立性。 |
| 原生 worker 是否运行、已停止或可恢复 | Runtime 原生状态 | Runtime | 工程记录可以引用执行句柄（handle），但不重建会话状态机，ticket 状态不能证明写入方已停止。 |

交接摘要须标明来源与候选快照，恢复执行时与当前内容核对，不能因 ID 相同就认定语义未变。修订只同步受影响的派生产物和证据，保留仍有效的结果和历史 done 记录，规范变化通过协调执行图或安排修正交付处理，不能用历史记录证明当前任务已经完成。

以下是维护者审计表，不要求每个 Skill 复制同一套章节或加载整张表，执行规则以各 Skill 为准。同一份测试或代码可用于不同判断，重复调查对象不等于职责重复。

## 职责审计

| Skill | 范围及可修改产物 | 决策与停止点 | 结论依据 |
| --- | --- | --- | --- |
| project-setup | 稳定 Profile、AGENTS.md 入口及获准迁移 | 固化已确认配置，不建设验证工具与方法，也不决定验收 | 项目已有约定、源文件及用户选择 |
| verification-setup | 本地验证方法、必要辅助脚本、验证导航和摘要 | 创建/刷新并试运行方法，将依赖、CI 或产品变更另交实现 | 实际启动、驱动、观察、清理与保留证据 |
| improve-agents-md | 获准的项目指令修改 | 判断指令是否有依据，不自行重配 Profile | 仓库规则、真实命令与适用范围 |
| find-docs | 只读文档检索 | 回答指定产品/版本的问题，不开展完整选型 | 官方资料、明确版本、未执行限制 |
| tech-research | 有边界的技术调研 | 提供推荐和采用条件，不直接实施 | 官方/工程资料、现状约束、已执行实验与推断区分 |
| grilling | 访谈及 decisions.md，并组合记录术语/ADR | 重要需求选择由用户决定，grilling 不决定局部实现，也不重写下游 | 当前事实、用户确认、未决 frontier |
| wayfinding | MAP.md 与决策文件 | 解决跨会话依赖决策，不交付产品 | 可追溯答案、调查或实验，HITL 不由 Agent 代答 |
| to-spec | SPEC、按需 ACCEPTANCE | 维护确认需求和验收语义，不设计内部实现 | 需求 authority、确认决策、外部契约 |
| high-level-design | HLD | 决定共享设计，长期方向须经 review gate，不改需求或拆票 | SPEC、真实调用方、项目约束和代码事实 |
| to-tickets | 通过脚本创建/协调 tickets | 决定交付拆分与真实依赖，不引入新需求/设计 | 已确认 SPEC/HLD、覆盖及图校验 |
| quick-implement | 单一目标实现、自检与收尾 | 不使用执行图，既有独立收尾规则仍适用 | 当前契约、真实 diff、自检与独立报告 |
| implement | 当前 ticket 的代码、必要测试和局部简化 | 决定局部实现，将契约问题交回调用方 | 已确认行为、项目方法和实际本地检查 |
| loop | attempt、状态、报告及交付记录 | 选工作、调用角色、判断结果、流转状态，不管理 Runtime | 全部相关 AC 证据、原始报告、有效候选快照 |
| verify | 只读验收，以及获准隔离资源中的探针/证据 | 逐条报告 PASS / FAIL / NOT VERIFIED，不修复或改状态 | 需求独立预期、可观察执行、证据可信度与覆盖限制 |
| code-review | 只读改动审查 | 找具体缺陷、回归和无必要复杂度，不代替逐条验收 | 可达场景、调用/保护/测试与反证 |
| test-audit | 指定测试审计，以及获准的限定清理 | 给出保留/合并/重写/删除建议，不成为固定交付门 | 独立预期、真实执行、独有保护与维护成本 |
| tdd | 实现中的行为测试、代码及局部重构 | 按 Red → Green → Refactor 执行，不拥有最终验收或任务调度 | 已实际运行的有效 Red/Green、独立预期与回归 |
| codebase-design | 指定 Module / Interface / Seam 的局部设计判断 | 推荐局部形状，不扫描整体架构或替代领域语言 | 真实调用、信息隐藏、变化原因与删除试验 |
| domain-modeling | 领域词汇与符合门槛的 ADR | 澄清模型，记录确认语义，不拥有访谈节奏或改需求 | 当前领域约定、契约、确认术语及真实取舍 |
| review-architecture | 只读架构审查，以及显式候选发现 | 判断现状与影响，不预先实施目标架构 | 项目约束、路径/所有权、适用官方指导与反证 |
| simplify | Review 或获准的限定修改 | 删除无当前职责的复杂度，不改变确认行为 | 实际使用方、持久化/外部契约与修改后验证 |
| debug | 复现、诊断，以及获准的最小修复 | 先建立问题反馈，不扩大到架构重做 | 已运行的症状复现、可证伪假设及原复现回归 |
| challenge | 只读地挑战已有判断 | 检验结论，不扩成需求访谈或完整重设计 | 已有约束、反证、影响及尚未确认事实 |
| how | 手动触发的当前代码解释 | 回答如何运行，不追溯历史或提出目标设计 | 当前真实生产路径与明确未观察范围 |
| why | 手动触发的历史依据调查 | 区分事实、推断、假设和未知，不因历史证明现状正确 | Git/ADR/issue 等历史与当前代码的关联 |
| fuck-my-shit-mountain | 显式项目审计、综合报告 | 负责选定维度覆盖，不自动修复或启动交付链 | 各维度证据、可达影响、反证及覆盖限制 |

## 上游适配与维护规范

对于源自 Matt Pocock 的 Skill，以上游原版为基础，只添加 Engineering Skills 确有需要的适配。自行设计的 Skill 不强行套用上游结构。

- 保留原版的核心机制、关键术语和交互节奏，改动前先核对原文，记录来源与适配理由。
- 适配集中在项目约定、文档位置、必要的技能组合及 Runtime 能力差异，不把下游流程说明塞进每个 Skill。
- 新增限制必须对应明确需求或已观察到的问题。通用常识、重复要求、分类教学和假设性防护不进入正文。
- 对重复出现且可确定性判断的问题，先考虑能否通过 script、schema、lint、test、validation 或 metadata 编码约束。结构化约束能够更可靠、更低成本地防止问题时，不要继续往 SKILL.md 叠加提示词。只有需要上下文判断、权衡或跨 Runtime 通用解释的规则才保留为 prose。不要为了消除一次偶发输出就引入新的工具或自动化机制。
- 通过组合复用已有规则，不复制另一 Skill 的细节，精简时也不能静默删掉已确认的能力，例如自动记录 decisions、术语对齐和 ADR。
- 优先修正有问题的局部，不要因一次输出不理想反复重写整体流程，也不以行数作为质量指标。
- 声称效果改善前，用相同任务、模型和上下文比较关键遗漏、无效追问、用户纠正及阅读负担。静态检查只能证明格式与规则一致，不能证明实际效果更好。

当前 grilling 基于 [Matt 的原版](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)，保留 design tree、frontier 和 round，以及每轮批量提出整个 frontier 的机制。本地适配包括紧凑的快捷回复格式、通用事实调查、项目内决策记录，以及与 domain-modeling 组合写入术语和 ADR。尚未完成行为对比验证。

TDD 基于 [Matt 的原版](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)适配，保留行为测试与逐步反馈。2026-09-26 核对上游后，按本仓库已确认的职责调整：取消逐个测试边界的重复确认，技术测试边界不写入 SPEC；允许 Green 后按需做局部重构；判断预期值的独立依据，不把字面量视为天然可信，也不把公式视为天然无效。较大设计变更仍交回调用方处理。这些调整不替代真实项目中的长期效果评估。

## 文档归属

`docs` 维护使用总览、跨 Skill 职责和 Loop / Runtime 关系，具体执行规则、格式与示例由所属 Skill 及其参考资料维护。仓库验证场景和历史评估记录由本地验证 Skill 引用，图示源文件与导出文件成套保存在 `docs/diagrams/`。变更时更新受影响的入口，不另建重复协议。

## 已收敛的职责

- Profile 字段语义、读取和迁移集中在 project-setup 的[引用说明](../engineering/project-setup/references/profile.md)，使用方读取相关设置，不绑定 AGENTS.md 内嵌格式，并保留旧持久化配置直到获准迁移。
- verification-setup 维护方法和能力摘要，verify 判断当前 AC 的充分证据。没有另一套验证命令配置或强制工具选择。
- verify 保留当前证据可信度检查，test-audit 保留系统测试价值审计，code-review 保留改动风险判断，不让任何一个报告替代另一个角色的验收责任。
- implement 已负责当前变化造成的必要简化，simplify 检查仍存在且有证据的问题。Loop 保留已有最终 simplify 角色契约，不新增逐 ticket 审计。
- Loop 删除固定无活动阈值、soft-ping 协议、活动时间及性能台账，不再要求固定 context 文件对，但保留原生 worker 执行、独立最终角色、证据失效重验和停止旧写入方的要求。
- codebase-design 的分析术语限定在设计讨论中，不要求项目把 service/API 等既有名称改成通用词汇。
- 其他现有入口有不同的判断目标和停止点，本轮保留，不因检查同一份代码就合并。

## 验证边界

图、attempt、事务和交付快照由现有 `python3 engineering/shared/check.py` 检查，Profile 迁移、按需读取及验收证据选择另用隔离任务演练。审阅文档不能证明 Runtime 生命周期、真实项目 GUI 质量、长期 token 或耗时改善，这些效果需后续真实任务记录支持。
