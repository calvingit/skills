# 对抗式审查

对已经形成的方案进行有边界的对抗式审查，找出会实质影响决策的薄弱点，不重新设计整套方案。

## 流程

1. 先明确当前结论、目标、约束和已经接受的前提，不重新发散讨论。
2. 检查关键假设是否有证据支持，是否忽略已有的职责归属、现有机制或架构约束。
3. 重点检查职责重叠、重复维护同一状态、运行时依赖、额外复杂度和迁移成本，并判断是否存在更简单且满足目标的方案。
4. 提出问题前，检查现有机制和证据是否已消除该风险。只报告影响明确且可验证的问题，以可读文本区分“必须处理”“建议考虑”和“可接受风险”。
5. 如果没有发现足以改变方案的问题，则保留当前方案；不要为了体现审查价值而制造异议。

## 独立升级

默认一次审查、一名 reviewer。不要因为方案篇幅大或感觉重要就自动组成审查组。

仅当方案影响大且一次审查后仍存在相互独立、证据不足的关键判断，或用户明确要求独立对抗审查时，才考虑用 2–3 名独立 reviewer 分别攻击同一方案。每人使用相同目标、约束、已确认事实和 proposal，且不得先看其他人的结论。不指定模型供应商；Runtime 不支持独立 subagent 时，说明限制并保持单人审查，不自行调用外部 Agent CLI，也不解析审查结果。

最终仍按“必须处理”“建议考虑”“可接受风险”综合一份可读报告。审查者之间的一致只提高置信度，不能代替证据。分歧对照代码、需求、测试和可观察事实解决，不按多数票裁定。

## 边界

默认只报告问题，不修改方案或实现。这里检验已有结论是否成立；需要通过访谈收敛尚未决定的需求或选择时，使用 `grilling`，不把一次审查自动扩成访谈流程。

不做通用代码审查，不替代技术调研，也不把低概率、低影响风险升级为阻塞项。除非发现核心前提不成立，否则不要扩大讨论范围。
