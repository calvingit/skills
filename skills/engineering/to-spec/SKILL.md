# To-Spec

把已收敛的需求一次性生成、验证并汇报 `SPEC.md` 与 `PLAN.md`，不自动实现。

## 入口检查

落盘前确认没有会改变方案的未决决策：

- 存在未决决策但可以在当前会话内解决 → 先建议用户调用 `grilling` skill 收敛。
- 存在需要跨会话推进的 Fog of war → 先建议用户调用 `wayfinding` skill。
- 需求本就清晰、无未决决策 → 直接汇总事实、默认假设和边界，进入收敛确认。

输入来自 `examine-architecture` 的报告路径和 candidate ID 时，先读取报告中对应候选的 evidence、friction、desired outcome 和 unknowns / non-goals，以其为需求来源进入收敛确认；报告路径不可读时停止并要求用户重新提供，不凭转述或记忆重建候选内容。

用户确认前不创建或修改正式 SPEC.md、PLAN.md。已选方案、放弃方案和默认假设必须已经记录；实际存在的非阻塞事项已有当前默认行为、不阻塞原因和重新决策条件。

## 产物范围

正式产物保持轻量：默认只有 `SPEC.md` 与 `PLAN.md`。不要生成 `TASKS.md`、问答 transcript 或新的决策汇总文件；`wayfinding` 已有的 `MAP.md` 与 `decisions/` 继续作为分析依据。multi-task、来自 wayfinding、预计跨多个 session、目标是其他 Agent Runtime，或用户明确要求跨 Agent 交接时，可按 [Implementation Handoff Prompt](references/implementation-prompt-template.md) 额外生成 `IMPLEMENT_PROMPT.md`；它是携带 `loop` 执行语义（退出条件、停止条件、断点、commit 授权、轮数上限）的可复制执行 envelope，接收方据此按 `loop` 自动推进到收尾，不是第三份需求文档。实现期间是否需要 `STATUS.md` 由 `implement` skill 根据 task 数量和跨 session 需要决定。

分析结论只确定行为、约束、决策、验收和高层任务依赖；不替实现指定代码片段、函数体、字段列表、新建文件清单和逐步修改方式，实现基于届时的项目状态重新调查。

## 任务目录与语言

按以下优先级确定任务目录和语言：

1. 用户明确指定的约定。
2. 当前项目已有的任务文档约定。
3. 无约定时使用 `docs/tasks/YYYY-MM-DD-<slug>/`。

沿用项目文档语言；项目没有明确语言时使用用户当前语言。流程名称和状态名称（R/AC/T、frontier 等 canonical English term）直接使用原词，首次出现时用完整句子解释含义，不创造中文别名。

## SPEC.md

SPEC 是尚待实现的目标行为契约；背景可以描述现状，但规范性主体不把当前代码观察冒充为已满足的目标需求。按以下语义顺序使用 H2 章节，标题翻译为项目文档语言：

1. 背景
2. 变更摘要
3. 目标生效需求
4. 边界与默认行为
5. 验收标准
6. 后续事项（仅实际存在时）

要求：

- `变更摘要` 只概括新增、修改、删除和保持不变的能力，是非规范性 delta；与后文冲突时以 `目标生效需求` 和 `验收标准` 为准。
- `目标生效需求` 与 `验收标准` 不得为空。每条需求使用稳定 ID `R1`、`R2`……，按相关性写清角色或权限、触发条件、输入及权威来源、状态变化、输出，以及失败、取消或数据缺失时的行为。
- 涉及接口、事件、存储或配置时写清外部可观察语义、空值、默认值和兼容边界，不写具体实现。
- `边界与默认行为` 只保留与当前任务有关的必须保持、明确不做和默认行为；没有内容的子类不建空标题。
- 架构类需求的边界应写清调用方不应知道的内部步骤、禁止的测试专用生产路径和必须保留的并发/失败语义；只写质量约束，不指定代码实体或实现配方。
- 每条验收标准使用稳定 ID `AC1`、`AC2`……，显式引用它覆盖的一个或多个需求 ID，例如 `**AC1** [R1, R2]`。每个 `R` 至少被一个 `AC` 覆盖。
- 验收标准描述前置状态或触发、外部可观察结果和必须保持的反向/失败行为。涉及具体期望值时写明独立来源（权威文档、既有契约、worked example 或用户确认的样例）；来源不明的先回 `grilling` 收敛，不在实现阶段才决定。落盘前逐条自检可判定性：不看实现能否判定结果成立；依赖实现细节或无法观察的 AC 先回 `grilling` 收敛，不落盘模糊验收。不得把测试文件、命令、静态分析、文档检查、代码位置或「存在测试」写成验收，除非该 artifact 本身就是用户要求的交付物。
- 所有阻塞性问题必须在落盘前解决。不会影响当前行为、边界、验收或 task 依赖的事项可写入可选的 `后续事项`；每项必须说明当前默认行为、不阻塞原因和重新决策条件。
- 不写未经确认的替代方案、问答过程或占位符。

## PLAN.md

PLAN 是绑定同目录 SPEC 的高层交付契约，不是可复制的代码配方。顶部引用同目录 `SPEC.md`，再按以下语义顺序使用 H2 章节，标题翻译为项目文档语言：

1. 交付与回退条件
2. 约束性事实
3. 已确认决策
4. 任务分解

要求：

- `交付与回退条件` 的完成部分要求全部 `AC` 均映射到 task unit，并在实现后取得与风险相称的证据；不要逐句复制 SPEC。
- 回退条件只记录本任务特有的方案失效、契约冲突或外部能力缺失条件。没有新证据、同路径重复失败、预算不足和通用外部阻塞由 `implement` skill 统一处理，不复制到每份 PLAN。
- `约束性事实` 只记录会改变交付方案的项目事实及其依据，不罗列普通代码上下文。易漂移事实同时记录必要的校验点，如版本、commit、配置或权威文档；依据不得变成预设修改目标。
- `已确认决策` 只记录会约束 task 边界、核心 Interface、依赖或风险的重要选择及原因，以及未来可能被重新提出的主要弃选方案和原因。来自 wayfinding 的重要决策可链接对应 decision ticket，来自 `examine-architecture` 的候选可链接报告路径和 candidate ID，都不复制问答或调查过程。
- 产品行为选择以 SPEC 为权威；PLAN 不重复建立第二套行为契约。
- 每个 task unit 使用稳定 ID `T1`、`T2`……，只描述交付结果、`Blocked by`、覆盖的 `AC`、必须保持的边界和验证目标。实现包含多个 fresh context windows 或需要显式 blocking edges 时，在写任务分解前完整读取 [Task Decomposition](references/task-decomposition.md)。
- 多个 task 共同依赖同一生产 Interface 时，先设置一个稳定该 Interface 的 blocking task，再分解可独立依赖该 Interface 的下游 task；不要把同一 Interface 的设计权并行分配。
- 验证目标只说明要取得的可观察证据类型，不写具体命令或测试路径。验证默认随所属 vertical slice 完成；只有独立设备、外部环境或人工验收无法随 slice 完成时，才建立单独验证 task。
- 任务分解不写文件修改清单、代码片段、伪代码、具体命令、测试路径或逐步实施方式；不保留占位符。

实现 Agent 接手后必须重新读取项目事实、检查当前状态并形成自己的具体实施方案。

## 变更控制

- `SPEC.md` 与 `PLAN.md` 是一组原子契约，首次生成和后续规范性修改都必须同步更新。
- 用户确认后的需求、边界或验收发生变化时，重新收敛方案（必要时回到 `grilling` / `wayfinding`）、同步 PLAN 并再次取得确认。
- 实现阶段发现的新事实只改变技术路径时，不改写 SPEC；若它会改变目标行为、边界、验收或 blocking edges，停止实现并返回需求收敛。
- 新文档使用本规则；历史 task 文档不批量迁移，`implement` skill 只支持当前格式，旧格式任务需要重新实现时先按当前格式重新落盘。

## 验证与汇报

重新读取生成文档，确认：

- 使用正确的项目路径、语言和现有约定。
- SPEC 的目标需求、边界和验收一致，`R` / `AC` ID 唯一且每个 `R` 都有 `AC` 覆盖。
- PLAN 覆盖全部 `AC`，`T` ID 唯一，每个 `T` 映射至少一个 `AC`，且 task 依赖无矛盾。
- 没有具体实现细节、占位符、阻塞性未决问题、无内容的后续事项或通用停止条件模板。
- wayfinding 工作文档与最终决策一致，但正式文档没有复制 round/question 流水；引用的 `examine-architecture` 候选与报告原文一致。

运行项目已有的文档校验；若项目使用 Git，检查相关 diff 的空白错误并覆盖新建文件。除非用户另行要求，否则不运行实现测试或构建，不修改业务代码，不提交或推送，不发布到在线 issue tracker。

大型或跨 Agent 任务若生成了 `IMPLEMENT_PROMPT.md`，按模板替换占位符，并在最终汇报中同时给出文件路径和完整可复制文本。完成后汇报任务目录、创建或更新的文件，以及实际存在的后续事项。
