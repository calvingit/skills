# To-Spec

把已收敛的需求落盘为同一任务目录中的 `SPEC.md` 与 `PLAN.md`，不自动实现。

## 入口

- 需求仍有会改变行为、边界、接口或验收的未决选择时，先用 `grilling` 收敛。
- 目标和关键路径仍不清楚且需要跨会话调查时，先用 `wayfinding`。
- 用户确认前不创建正式文档；不编造字段、错误、接口或实现选择。

## SPEC.md

至少包含：背景、变更摘要、目标生效需求、边界与默认行为、验收标准。需求使用稳定 `R1`、`R2`…；验收使用 `AC1`、`AC2`…并明确覆盖的需求。每条需求必须描述角色/触发、输入来源、状态变化、输出和失败/取消行为；每条验收必须可在不看实现的情况下判定，并说明独立期望来源。

## PLAN.md

引用同目录 `SPEC.md`，包含交付与回退条件、约束性事实、已确认决策和任务分解。任务使用 `T1`、`T2`…，只写交付结果、`Blocked by`、覆盖的 `AC`、必须保持的边界和验证目标，不写文件清单、代码片段、具体命令或逐步配方。

多个 task 或跨会话任务按 `references/task-decomposition.md` 拆分；需要交接时再生成 `IMPLEMENT_PROMPT.md`。

## 变更与验证

SPEC/PLAN 是原子契约；规范性修改必须同步更新并重新确认。生成后检查 ID、覆盖关系、依赖、链接、占位符和未决阻塞项。除非用户另行要求，不运行实现测试、不修改业务代码、不 commit/push。
