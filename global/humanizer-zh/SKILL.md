# humanizer-zh

让文本像具体的人在当前场景里说话，而不是像模型在组织答案。它只负责改写，不替目标仓库决定写作规范。

## 使用边界

适合处理博客、评论、Newsletter、产品分析、长邮件和工作汇报等中文文本，去掉 AI 味，让表达更像母语写作，也可用于标注文字问题。

不适合逐字翻译、必须保留官方口径的文本、以代码/日志/配置为主体的内容，以及以事实核查为主的任务。

## 规则来源

1. 目标仓库有 writing style、editorial guide 或 AGENTS 写作规则时，先读并遵循，仓库规则决定“什么是好文本”。
2. 本 Skill 只负责识别 AI 痕迹、选择改写力度、保护事实并完成改写。
3. 没有仓库级规范时，遵循自然中文句法，少模板、少空话、少碎片化断句，也不为口语感牺牲专业度。

## 不可破坏项

改写前先保住：

- 事实、数字、时间、引用和链接
- 产品名、人名、版本、命令、路径、接口名、字段名和错误信息
- 原文立场、责任主体和结论强弱
- 用户明确要求逐字保留的内容

不补新事实，不编来源，不偷换主语，也不把“可能”改成“已经”。

## 模式

- `annotation`：用户要求先指出问题，不直接重写
- `rewrite`：直接给改写后的推荐版本

默认：`rewrite + standard + bounded`。

改写力度：

- `minimal`：原文基本可用，只做局部清理
- `standard`：默认，允许重写句子、合并弱句和调整段内顺序
- `aggressive`：只用于通稿腔、拼接稿或结构明显失真的文本

范围（scope）：

- `in-place`：只做句内修改，不删整句，也不合并相邻句
- `bounded`：默认，可删空话、合并弱句，但不重建全文逻辑
- `structural`：用户明确要求重写，或原结构明显失真时使用

## 执行

1. 先读目标仓库的共享写作规范，没有就使用本 Skill 的默认原则。
2. 标出 protected spans：事实、数字、引用、术语、命令和责任主体。
3. 先看段落结构，再看句法和词语，找出模板化表达、翻译腔、碎片化断句、无源权威、口号式收尾和过度排版。
4. 按用户要求选好模式、力度和 scope，再改写。
5. 回读两遍，第一遍检查事实有没有走样，第二遍检查文字是否还像模型在组织答案。

特别注意中文断句：

- 语义连续、主语一致、属于同一逻辑链的短句，优先用逗号连接或改成自然复句，不用连续句号制造节奏。例如 `代码不是没用。测试确实在用。但它没有生产价值。` 更适合改成一个语义完整的复句。
- 不要为了减少句号，把本该独立成句的意思改成分号。分号只用于语义并列且关系紧密的分句，定义、流程、职责或独立条件切换时，仍用句号断开。

## 输出

默认只给一个推荐版本，只有用户明确要求时，才附问题清单、轻改/重写双版本或修改说明。

`annotation` 模式下，每条只回答“哪里像 AI + 为什么”，按 `fatal / obvious / mild` 标严重度，不展开成长篇理论。

## 最终检查

交付前确认：

- 事实、数字、引用、责任主体和判断强弱没有变化
- 没把专业文本改得过度口语化
- 没有明显连续短句、设问自答和一句一段
- 同一逻辑链的短句已自然合并，独立意思没有用分号硬接
- 没有无来源权威、模板化开场或口号式收尾
- 没有为了“自然”机械换同义词
- 目标仓库的共享写作规范已优先于本 Skill 的默认规则
