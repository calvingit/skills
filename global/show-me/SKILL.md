# Show Me

先明确用户要理解的问题、关键关系和必要信息，再选择足以解释它的最小表达形式。遵守用户指定的格式，未指定时按理解难点选择一种或少数组合形式，不默认把所有形式都用一遍，也不把 HTML 当成更高级的必选输出。

## 选择形式

| 理解难点 | 优先形式 |
| --- | --- |
| 结论、判断或简单操作 | 简洁文本或短列表 |
| 精确对比、字段映射或多项权衡 | 表格 |
| 逻辑或算法 | 伪代码或相关代码片段 |
| 运行时顺序、依赖、分支、数据流或状态变化 | Mermaid 等可渲染图示 |
| 界面结构或文件职责 | 浅层组件树、文件树，只保留相关状态和职责 |
| 已有结构的变化 | diff；缺少上下文会影响理解时，给出完整的相关结构 |
| 外观、空间关系或视觉概念 | 图片；精确结构和数据使用确定性绘图工具 |
| 参数变化、逐步展开或场景比较需要用户探索 | 聚焦单一问题的交互式 HTML |

文字已足够清楚时直接交付，不额外创建图示或文件。静态关系能用表格或图示说明时，不为装饰创建网页；用户明确要求 HTML 时仍按要求交付。需要具体写法时读取 [形式示例](references/examples.md)。

## 整理与表达

- 围绕关键问题组织信息，先给判断，再解释关系、条件和限制。不要把原文直接塞进卡片，或靠图表数量代替清楚的解释。
- 使用具体词语、明确的主语和自然的句子，减少无用术语与长句，保留影响判断的细节。不为追求短句切断条件与结果，也不强制套用 ASD-STE100 等受控语言规范。
- 保持图示聚焦，避免低信息量或难以阅读的长链。图内使用短标签，把必要背景放在图外说明。

## 事实与证据

项目说明必须基于读过的代码或资料，区分现状、拟议变化、假设和示意数据，不把示例画成已实现结构。解释性展示帮助理解，截图、录屏和实际测试结果证明运行行为；不要把示意图或模拟交互当成验证证据。解释性产物检查通过，也不代表它描述的系统已通过验证。

## 产物与检查

- 已选择 HTML 输出时，先判断表达目标是否适合模板。常规总览、顺序讲解和精确对比可读取 [模板格式与调用方法](references/html-format.md)，用 `scripts/render.py` 填充 `references/explanation.html`；空间布局、连续叙事、交互探索或特殊视觉结构是理解关键时，直接编写定制 HTML，无需先尝试模板。
- 模板是可选工具，不规定章节数量或必选组件。不要为使用模板拆碎内容、删掉必要信息或改变阅读顺序；短内容可以是一个连续正文区，导航、编号和卡片边框按需关闭。节省输出不能优先于理解效果。
- 适合复用时，将内容组织与排版实现分开，保留可编辑源稿。不必用原始 HTML 块强行适配外层模板，也不要为一次性输出引入不必要的安装或依赖。
- 常规图示优先使用 Mermaid 或确定性的自动布局工具，减少重复编写样式和手算 SVG 坐标。
- 沿用已有视觉风格，优先使用目标环境支持的渲染形式和工具。只有交互能帮助理解或用户明确要求时，才增加交互控件，每个控件都应改变相关内容或状态。
- HTML 优先做成可直接打开的单文件，避免不必要的依赖。检查桌面与移动端可读性，以及关键交互、默认状态和边界输入；检查图示渲染、标签和关系，检查表格与数据是否对应来源。
- 按用户指定位置或当前环境的保存约定保存，通过可用预览或文件链接交付。报告实际完成的检查及结果，无法运行或观察的部分明确写未验证。
