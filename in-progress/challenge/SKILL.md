# 对抗式审查

对已经形成的方案进行有边界的对抗式审查，找出会实质影响决策的薄弱点，不重新设计整套方案。

## 流程

1. 先明确当前结论、目标、约束和已经接受的前提，不重新发散讨论。
2. 检查关键假设是否有证据支持，是否忽略已有的职责归属、现有机制或架构约束。
3. 重点检查职责重叠、重复维护同一状态、运行时依赖、额外复杂度和迁移成本，并判断是否存在更简单且满足目标的方案。
4. 只提出影响明确且可验证的问题，区分 `must_address`、`should_consider` 和 `acceptable_risk`。
5. 如果没有发现足以改变方案的问题，则保留当前方案；不要为了体现审查价值而制造异议。

## 边界

不做通用代码审查，不替代技术调研，也不把低概率、低影响风险升级为阻塞项。除非发现核心前提不成立，否则不要扩大讨论范围。
