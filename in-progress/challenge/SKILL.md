# Challenge

对当前已经形成的方案做一次有边界的反方审查。目标不是重新设计全部方案，而是找出会实质影响决策的薄弱点。

## Process

1. 先复述当前结论、目标、约束和已经接受的前提，不把讨论重新拉回开放式 brainstorming。
2. 检查关键假设是否有证据支持，是否遗漏现有 owner、现有机制或已有架构约束。
3. 重点检查职责重复、状态重复、运行时依赖、额外复杂度、迁移成本，以及是否存在更简单且满足目标的方案。
4. 只提出影响明确且可验证的问题，区分 `must_address`、`should_consider` 和 `acceptable_risk`。
5. 如果没有足以改变方案的问题，明确维持原结论；不要为了证明审查有价值而制造异议。

## 边界

不做通用代码审查，不替代技术调研，也不把低概率低影响风险升级为阻塞项。除非发现当前方案的核心前提不成立，否则保持讨论范围不扩张。
