# 建模与缓存

## 先确定数据契约

按实际访问方式选择结构：独立字段更新、排序、集合成员判断与整块序列化的成本不同。核对单个对象大小、集合增长、热点及返回体积；不要仅凭对象形状决定 Hash 或 JSON。Key 命名沿用项目约定，区分租户和业务标识，不把凭证写入 Key。

TTL 到期、主动删除和内存淘汰分别以不同方式结束数据的生命周期。先确定哪些数据允许丢失、由谁重建、是否允许陈旧，以及缺失与业务上的空结果如何区分。不要为所有 Key 机械添加相同 TTL；更新命令是否保留或重置过期时间需按实际命令核对。

## 检查缓存读写竞争

画出源数据提交、缓存读取、回填与失效的实际顺序。即使在数据库写入成功后删除缓存，也可能与旧值回填交错发生；仅设置 TTL 不能证明满足一致性要求。按允许数据滞后的时间范围选择现有版本校验、失效或重建机制，不默认引入双写、延迟双删或分布式锁。

缓存不可用时，应结合回源容量、并发上限和业务可用性约定决定如何处理，不能一律绕过缓存，也不能把依赖异常伪装成空结果。确有重复回源压力时再考虑请求合并、过期时间分散或负缓存（negative caching），并明确缓存的是“资源不存在”等哪类否定结果，以及权限、有效期和新数据可见性。

验证相关交错与失效路径，观察源数据、缓存值和用户结果；高命中率不能证明缓存内容正确。
