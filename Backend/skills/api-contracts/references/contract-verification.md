# 契约验证

根据改动选择足以作出判断的最少证据，沿用项目工具，不强制引入 Pact、代码生成器或 Schema Registry。

## 检查链

1. 校验源文件的语法、引用和版本支持；使用已有差异工具识别可能不兼容的变化，再人工判断行为和调用方影响。
2. 从确认的源文件重新生成客户端、类型或文档，检查产物差异与生成器版本。不要直接手改生成文件；无法生成时记录哪些产物尚未同步。
3. 通过实际服务边界核对请求校验、响应序列化、状态和错误，以及涉及的授权与副作用。只测试 DTO 或内部 mock 不能证明网关和实际请求处理函数（handler）的行为符合契约。
4. 验证受支持的旧客户端或消费者，而不仅是本次重新生成的最新版。按风险覆盖未知枚举、缺失/null、额外字段和历史消息。

区分 Schema 校验（schema validation）、服务提供方的契约符合性验证（provider conformance）和消费者驱动契约（consumer-driven contract）：格式合法不证明服务实现符合契约，服务提供方通过验证也不证明所有调用方都能正常使用。消费者契约需反映调用方的真实依赖，并由对应版本的服务提供方验证；用同一实现生成 mock 再验证自身，不能形成独立依据。

如果 Schema 和代码都接受了契约明确禁止的值，即使二者一致，行为仍然是错的。预期结果必须来自已确认契约；发现冲突时保留证据并交还契约负责方，不静默扩大 Schema。

## 最小验证材料

为受影响项记录输入、调用方版本、预期结果及来源、实际可观察结果和命令。兼容检查最好保留一个能触发差异的旧调用方样本；没有旧客户端可执行时，静态分析只能形成有限结论。

测试生成的请求可能创建、删除或触发外部副作用。使用隔离服务或获授权目标及数据，不把契约验证当作任意生产调用许可。只检查事件消息格式的测试，无法验证消息代理（broker）的投递行为和消费者的确认语义。

资料：[Pact 的契约测试与消费者契约](https://docs.pact.io/)。
